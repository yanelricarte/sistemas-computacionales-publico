Parte 1 Exposición de información

1. Llave fuera del repositorio

En GitHub. Desde el navegador, entren al repositorio del equipo y busquen conexion.php (o como se llame el archivo donde están el usuario y la contraseña de MySQL). La comprobación es sobre lo que subiste, así que se hace en GitHub y no en la carpeta de la máquina.

El resultado esperado. El archivo no aparece en GitHub.

La corrección. Tres pasos, en este orden:

# 1) que Git deje de seguirlo de ahora en adelante
echo "conexion.php" >> .gitignore

# 2) sacarlo del repositorio sin borrarlo de la maquina
git rm --cached conexion.php
git add .gitignore
git commit -m "La conexion sale del repositorio"
git push

# 3) cambiar la contrasena: lo que estuvo subido quedo en el historial

Para que un compañero sepa qué archivo le falta, suban un conexion-ejemplo.php con la forma y sin los datos reales.

El motivo. Un programa tiene dos clases de contenido. El código es el mismo en todas las máquinas donde el sistema corre, y por eso se comparte: para eso existe el repositorio. La configuración cambia en cada máquina —la dirección de la base, el usuario, la contraseña— y además es secreta. Un repositorio distribuye: todo lo que entra ahí se copia a cada clon y queda registrado en cada versión. Mezclar las dos clases de contenido en un mismo archivo hace que el secreto se distribuya con el código.

Ampliación Archivo de configuración y .gitignore

Lo que estás haciendo con conexion.php tiene un nombre y una convención. En casi todos los lenguajes ese archivo se llama .env —de environment, el entorno donde corre el sistema— y guarda lo que cambia de una máquina a otra: la dirección de la base, el usuario, la contraseña, las claves de los servicios que el sistema usa. Laravel, Node y Python trabajan así. En el PHP que escriben ustedes, conexion.php cumple exactamente ese papel.

La regla es siempre la misma, y tiene dos mitades:

  • El archivo con los valores no va al repositorio. Vive en cada máquina, con los datos de esa máquina.
  • Va un archivo de ejemplo, con las claves vacías. .env.example, o conexion-ejemplo.php. Quien clona el proyecto lo copia, le pone sus datos y arranca — sin ese ejemplo, no tiene forma de saber qué le falta.

El .gitignore es la lista de lo que Git deja afuera. Un proyecto web suele tener por lo menos esto:

.env
conexion.php

node_modules/
vendor/

.vscode/
Thumbs.db
node_modules, la carpeta que se regenera sola
Esa carpeta son las dependencias: código que escribió otra gente y que el proyecto usa. Se vuelve a bajar entera con un solo comando a partir de package.json, que sí va al repositorio, así que guardarla es de más: son decenas de miles de archivos que hacen lento cada clonado. Con vendor/ de PHP pasa lo mismo: se reconstruye desde composer.json.

El criterio que ordena las dos cosas: al repositorio va lo que escriben ustedes y lo que hace falta para reconstruir el resto. Queda afuera lo que se regenera solo, y lo que es secreto.

Pregunta. Ya sacaste conexion.php del repositorio y pusheaste. La contraseña que estaba adentro…

2. Mensajes de error en pantalla

En todo el código. Busquen mysqli_error y or die en el código.

El resultado esperado. El visitante lee una frase común. El detalle técnico queda para ustedes.

El síntoma. Lo más probable es que tengas esto:

mysqli_query($conexion, $sql) or die(mysqli_error($conexion));

El motivo. Un sistema devuelve dos clases de información cuando algo falla. Una es para quien lo usa, y solo necesita saber que la operación no se completó. La otra es para quien lo programa, y describe qué falló y dónde. Cuando las dos van a la misma pantalla, el sistema le entrega a cualquier visitante una descripción de su propia estructura. Reunir esa descripción es la primera etapa de cualquier intento de entrar a un sistema, y provocarle errores a propósito es la forma más barata de conseguirla.

Ese mensaje muestra los nombres de las tablas y de las columnas, y a veces la ruta del archivo en el servidor.

La corrección. El detalle va al registro del servidor, y al visitante le llega un aviso común:

if (!mysqli_stmt_execute($sentencia)) {
  error_log(mysqli_error($conexion));
  header('Location: listado.php?error=guardar');
  exit;
}

Mientras desarrollan conviene ver el error completo. Lo que cambia es que el sistema quede así el día que lo muestran.

Verdadero o falso. El mensaje de error de MySQL le sirve a alguien que quiere entrar al sistema, aunque el visitante común lo ignore.

Parte 2 Configuración de la base

3. Juego de caracteres de la conexión

En conexion.php. Busquen la línea mysqli_set_charset.

El resultado esperado. Está, justo después de conectar:

<?php
$conexion = mysqli_connect('localhost', 'root', '', 'tu_base');
mysqli_set_charset($conexion, 'utf8mb4');

El motivo. Un juego de caracteres es un acuerdo sobre qué bytes representan qué caracteres. En utf8mb4 la «ó» ocupa dos bytes; en latin1, donde un solo byte alcanza para 256 caracteres, ocupa uno.

Dos cosas distintas que se eligen juntas
Cuando crearon la base eligieron utf8mb4_unicode_ci, y eso es un cotejamiento, no un juego de caracteres. El juego de caracteres es utf8mb4, la primera parte del nombre, y dice cómo se guardan los caracteres. El cotejamiento es el resto, unicode_ci, y dice cómo se comparan y se ordenan: si «Ana» y «ana» son iguales para un WHERE —las letras ci son por case insensitive— y en qué orden salen las tildes en un ORDER BY. Cada cotejamiento pertenece a un juego de caracteres, y por eso el nombre empieza nombrándolo.

El problema aparece porque en este recorrido hay dos acuerdos en juego, y no tienen por qué coincidir. Uno es el de la tabla, que quedó fijado al crear la base. El otro es el de la conexión, que la biblioteca cliente establece con lo que traiga configurado. Si la tabla guarda en utf8mb4 y la conexión pide los datos como latin1, los dos bytes de la «ó» viajan y se reinterpretan como dos caracteres sueltos, que es lo que se ve en pantalla como «Ã³». mysqli_set_charset declara el juego de caracteres de la conexión y la pone de acuerdo con la tabla.

La corrección. Agréguenla. Sin esa línea las tildes y las eñes salen rotas en el sitio aunque la tabla guarde en utf8mb4. Se nota enseguida en el listado, que es la pantalla que va al documento.

Antes de correrla Anoten en la carpeta qué creen que van a ver, y por qué. Después corran la prueba y comparen.

La prueba: carguen un producto con tilde y mírenlo en la web.

Si no pasa lo que esperaban
  1. Miren el dato en phpMyAdmin. Si ahí está roto, el problema es anterior: entró mal.
  2. Si en phpMyAdmin está bien y en la web sale roto, el problema es el canal, que es lo que corrige esta comprobación.
  3. Si sigue roto con la línea puesta, miren que la etiqueta <meta charset="UTF-8"> del HTML también diga UTF-8.

Escribilo. La línea que va justo debajo de mysqli_connect en el conexion.php del equipo. Escríbanla con $conexion como nombre de la variable.

4. Motor de las tablas y clave foránea

En phpMyAdmin. Elijan la base y miren la columna Motor de la lista de tablas.

El resultado esperado. Dice InnoDB en las tablas que tienen clave foránea.

El motivo. La integridad referencial es una garantía que el gestor hace cumplir en cada operación de escritura: mientras exista un producto que apunta a un rubro, ese rubro no se puede borrar. Quien la hace cumplir es el motor de almacenamiento, que es el componente del gestor que guarda las filas y aplica las restricciones. InnoDB implementa claves foráneas; MyISAM, que es más viejo, no las implementa. Una restricción que el motor no aplica queda como una anotación en el archivo .sql, con la misma fuerza que un comentario: la relación del modelo existe en el diagrama y no en los datos.

El síntoma. Con MyISAM, el FOREIGN KEY que escribieron en el CREATE TABLE se acepta y se descarta en silencio.

Antes de correrla Escriban qué esperan que pase al borrar ese rubro. La respuesta dice si creen que la relación existe.

La prueba que decide: intenten borrar un rubro que tenga productos.

CON LA RELACION VIVA          SIN RELACION (MyISAM)

  ERROR 1451                    el rubro se borra
  Cannot delete or update       y los productos quedan
  a parent row: a foreign       apuntando a un id que
  key constraint fails          ya no existe

La corrección. Operaciones → Motor de almacenamiento → InnoDB, y vuelvan a declarar la clave foránea en Estructura → Vista de relaciones.

Datos que llegan de afuera

El sitio corre en su servidor. El navegador de quien lo visita corre en la computadora de esa persona. Son dos programas en dos máquinas, y se comunican por HTTP mandándose texto: el navegador arma un pedido, lo manda, su PHP lo lee y contesta. Después la conexión se cierra.

Esa persona controla su navegador. Puede escribir en los campos lo que quiera, cambiar la dirección en la barra, abrir las herramientas de desarrollo y editar el HTML antes de enviarlo, o armar el pedido con una herramienta cualquiera sin pasar por su página. Ninguna de esas cosas requiere saber programar.

Así que lo que llega a su PHP es texto escrito por otra persona, y entra por cuatro puertas.

Con ese texto hay dos cosas para hacer, y la mitad de las fallas que van a buscar hoy salen de confundirlas.

Tratar el texto como dato

Una consulta armada pegando variables llega a la base como una sola cadena, y el analizador de MySQL la lee entera para decidir qué operación ejecutar. Ahí el texto que escribió el visitante queda mezclado con las palabras de la consulta, y si contiene una comilla o un punto y coma cambia la estructura de la orden. Eso es la inyección SQL.

Una sentencia preparada separa el proceso en dos etapas. Primero manda la consulta con signos de pregunta en el lugar de los valores, y la base la analiza y planifica ahí, sin los datos. Después manda los valores, que se acoplan a un plan ya decidido y no se vuelven a analizar como SQL. Por eso una comilla adentro de un valor es una comilla y nada más (comprobación 5). Es la defensa principal que recomienda OWASP para inyección, y la única que no depende de acordarse de escapar cada vez.

Del lado de la salida pasa algo equivalente. Un dato que se imprime dentro del HTML se vuelve parte del documento que el navegador interpreta, y una etiqueta escrita en un campo de texto se ejecuta como si la hubieran escrito ustedes. htmlspecialchars convierte esos caracteres en entidades para que se muestren en lugar de interpretarse (comprobación 6). El escape depende de dónde aterriza el dato, porque no se escapa igual el cuerpo del HTML que el valor de un atributo. Desde PHP 8.1 el valor por omisión de htmlspecialchars ya escapa las comillas simples además de las dobles; en versiones anteriores había que pedirlo con ENT_QUOTES, y por eso todavía se ve escrito así en mucho código.

Comprobar el texto antes de usarlo

Que el campo llegó, que el número es un número, que el id existe y que corresponde a esta persona. Esa comprobación corre en el servidor. La que hace el navegador —required, maxlength, el desplegable con tres opciones— es una ayuda para quien completa el formulario de buena fe, y se desactiva desde las herramientas de desarrollo o se saltea armando el pedido a mano (comprobaciones 7 y 8).

Parte 3 Datos que llegan de afuera

5. Consultas con datos que vienen de afuera

En los archivos del CRUD. Los cuatro que hacen INSERT, UPDATE, DELETE y el SELECT que busca por id. Miren cómo se arma cada consulta.

El resultado esperado. El dato viaja aparte de la consulta, con un signo de pregunta en su lugar.

El síntoma. La variable pegada adentro del texto de la consulta:

$sql = "INSERT INTO producto (nombre) VALUES ('$nombre')";   // asi no

Escrito así, lo que el visitante teclea se convierte en parte de la consulta. Un producto que se llame Detergente D'Oro ya rompe el INSERT por el apóstrofo; alguien que sepa lo que hace escribe un nombre que borra una tabla.

El motivo. Está desarrollado en Datos que llegan de afuera. En una consulta armada por concatenación, el texto del visitante y las palabras de la orden llegan mezclados en una sola cadena, y el analizador de la base los lee juntos. Una sentencia preparada separa el análisis de la sentencia de la entrega de los valores, y un valor que llega después no puede modificar una operación ya planificada.

La corrección. Cada consulta que recibe algo del formulario o de la URL pasa a tres pasos: el molde con los ?, los datos con su tipo, y la ejecución.

Antes de correrla Miren cómo está escrita su consulta y anoten qué creen que va a pasar. Recién después prueben.

La prueba: carguen un producto con un apóstrofo en el nombre. Con la sentencia preparada se guarda entero; sin ella, salta un error de sintaxis de SQL.

Si no pasa lo que esperaban
  1. Si esperaban el error y no salió, fíjense si esa consulta ya estaba preparada, o si el sistema tiene otra capa que escapa el dato antes.
  2. Si la pasaron a preparada y igual falla, cuenten los ?, las letras de la cadena de tipos y las variables. Los tres números tienen que coincidir.
  3. Si guarda pero con los datos cambiados de columna, el orden de las variables no es el de los ?.

Encontrá el error Este alta funciona y guarda las filas. Lean las cuatro líneas antes de contestar.

<?php
$nombre = $_POST['nombre'];
$sql = "INSERT INTO producto (nombre) VALUES ('$nombre')";

header('Location: listado.php'); exit;

¿Cuál es el problema?

Ahora arréglenlo. Escriban la línea 3 como tiene que quedar, con el molde de la sentencia preparada.

6. Datos impresos en la página

En el listado y en la ficha. Busquen los lugares donde se imprime lo que trae la base.

El resultado esperado. Cada dato pasa por htmlspecialchars.

El motivo. La sentencia preparada cuida lo que entra a la base; esto cuida lo que sale hacia la página. Un dato con < o con comillas se mete en el HTML y descuadra la tabla; con un poco más de intención, se mete una etiqueta <script> que corre en el navegador de quien visite el sitio.

7. Comprobación del lado del servidor

En los archivos que procesan formularios. Miren arriba de todo, antes del INSERT o del UPDATE.

El resultado esperado. Antes de tocar la base, PHP comprueba lo que llegó: que el campo esté, que el número sea un número, que el valor tenga sentido.

El motivo. El required y el maxlength del formulario son una ayuda para quien lo completa de buena fe. Se desactivan desde las herramientas del navegador en diez segundos, y también se saltean mandando el pedido sin pasar por su página. La comprobación que gobierna es la de PHP, porque corre en el servidor y nadie la puede tocar.

El exit; que falta
Cada header('Location: ...') lleva un exit; en la línea siguiente. Sin él, PHP redirige y sigue ejecutando el archivo: la validación aparenta funcionar y la escritura se hace igual. Es una falla que no da ningún error.

}

$sentencia = mysqli_prepare($conexion, "INSERT INTO producto (nombre) VALUES (?)");
mysqli_stmt_bind_param($sentencia, 's', $nombre);
mysqli_stmt_execute($sentencia);

8. Id oculto del formulario

En el formulario de edición. Busquen el campo <input type="hidden" name="id">.

El resultado esperado. El archivo que procesa la edición comprueba que ese id sea un número y que la fila exista, antes de escribir.

El motivo. Escondido quiere decir que no se ve en la pantalla. Cualquiera que abra las herramientas del navegador cambia ese número, manda el formulario con otro id y edita una fila que nunca abrió.

La corrección. El id se comprueba antes de escribir:

$id = filter_input(INPUT_POST, 'id', FILTER_VALIDATE_INT);
if (!$id) {
  header('Location: listado.php?error=id');
  exit;
}

La pregunta que queda abierta —quién tiene permiso para mandar ese id— se resuelve en las secciones 11 y 12.

9. Enlace que borra

En el listado. Fíjense cómo está hecho el enlace o el botón de borrar.

El resultado esperado. El borrado sale de un formulario por POST, con una confirmación antes.

El síntoma. Un enlace común, como cualquier otro:

<a href="borrar.php?id=3">Borrar</a>

Escrito así, la dirección borrar.php?id=3 borra una fila con solo escribirla en la barra.

El motivo. La especificación de HTTP define a GET como un método seguro, en el sentido preciso de que pedirlo no debería producir ningún efecto sobre los datos. Los rastreadores de los buscadores, los antivirus y el propio navegador cuando adelanta enlaces cuentan con eso, y siguen los enlaces de una página sin preguntar. Un borrado detrás de un enlace se ejecuta solo.

Alcance de POST, y el ataque que no evita
Pasar el borrado a POST evita que se dispare por accidente y respeta lo que el protocolo dice de cada método. No impide que alguien arme el pedido a propósito. Un formulario alojado en otro sitio puede enviar un POST al de ustedes, y si esa persona tiene la sesión abierta, la cookie podría viajar sola con el pedido. Ese ataque se llama CSRF. Los navegadores actuales lo dificultan por su cuenta —de manera predeterminada no mandan la cookie en un pedido que viene de otro sitio, con una política llamada SameSite—, pero eso es una defensa del navegador y no del sistema. La que corresponde escribir es un valor de un solo uso que la página genera y el servidor comprueba. Queda para más adelante; hoy alcanza con conocer el límite.

Verdadero o falso. Con el borrado por POST, escribir borrar.php?id=3 en la barra de direcciones deja de borrar la fila.

El borrado por POST, con confirmación y con el id comprobado — se abre con el código de la clase.

Memoria entre dos pedidos

HTTP es un protocolo sin estado. Cada pedido se interpreta por sí solo, con la información que trae adentro, y el servidor no guarda nada de un pedido para el siguiente: contesta, cierra la conexión y se olvida. Cuando esa misma persona hace clic en el enlace siguiente, llega un pedido nuevo que para el servidor no tiene ninguna relación con el anterior.

Entonces, si alguien se identifica en login.php, ¿cómo se entera editar.php, en el pedido siguiente, de que esa persona ya entró? El protocolo por sí solo no lo resuelve. Lo resuelve un mecanismo agregado, las cookies, que le permiten al servidor pedirle al navegador que guarde un dato y lo devuelva en cada pedido posterior al mismo sitio.

Sobre eso PHP construye las sesiones. Al llamar a session_start(), el servidor genera un identificador, lo manda en una cookie —que por omisión se llama PHPSESSID— y crea de su lado un espacio de almacenamiento asociado a ese identificador. Lo que el programa escribe en $_SESSION queda ahí, en el servidor, y nunca viaja al navegador.

De ahí se siguen dos cosas que gobiernan lo que queda del día.

session_start() va en cada página que necesite saber quién entró. Cada pedido llega solo, y hay que volver a abrir el espacio de la sesión en cada uno. Por eso la guardia se incluye en todas las páginas que escriben, y no solamente en el login.

Y un valor guardado en $_SESSION lo escribió su propio programa y quedó del lado del servidor, mientras que un valor de un campo oculto viajó hasta el navegador y volvió. Del valor de la sesión se puede confiar, y el del campo oculto se comprueba, porque tienen orígenes distintos. Es la distinción de Datos que llegan de afuera aplicada a la sesión.

10. Contraseñas guardadas

En el login. Abran el archivo que procesa el login y busquen de dónde saca el usuario y la contraseña.

Esta comprobación hoy da un hallazgo
Lo más probable es que el sistema todavía tenga los usuarios escritos adentro del código, como quedaron en la Clase 2. Eso es el resultado de la comprobación: se anota en la tabla de estado y se corrige en la sección 11, cuando la tabla usuarios se crea. Lo que sigue es el estado al que hay que llegar.

Consecuencias de guardarla legible

Una tabla de usuarios con las contraseñas escritas tal cual se tecleó es un problema que excede al sistema. Quien llegue a esa tabla —por una copia mal guardada, por una consulta expuesta, por cualquiera de las diez comprobaciones de esta página— se lleva las contraseñas de personas reales. Y como casi todo el mundo repite la misma contraseña en varios lugares, con esa lista también entra al correo y a las redes de esas personas.

Por eso el sistema tiene que poder comprobar una contraseña sin conservarla. Suena contradictorio, y es exactamente lo que resuelve el hash.

Cifrar y hashear, dos cosas distintas

Las dos palabras se usan como sinónimos y nombran cosas distintas.

CifrarHashear
Para quéGuardar algo que después hay que volver a leerComprobar algo que nunca hace falta volver a leer
Vuelta atrásSí, con la claveNo existe: no hay clave que lo deshaga
EjemploUn mensaje que el destinatario tiene que poder leerUna contraseña, que solo hay que comparar

Una contraseña nunca hace falta volver a leerla. Cuando alguien entra al sistema, no se compara la contraseña guardada con la tecleada: se vuelve a calcular el hash de la tecleada y se comparan los dos resultados. Por eso se hashea y no se cifra — y por eso, cuando en un sitio piden la contraseña olvidada, mandan una nueva en lugar de la vieja.

Funciones de hash

Una función de hash toma un texto de cualquier largo y devuelve una salida de largo fijo. La misma entrada da siempre la misma salida, y por eso sirve para comparar sin guardar el original: al validar el login se vuelve a calcular y se mira si coincide con lo guardado. Cambiar una sola letra de la contraseña cambia toda la salida, así que dos contraseñas parecidas dan resultados que no se parecen, y mirar el hash no acerca a la contraseña.

Para el camino inverso no hay cálculo. La única vía es probar textos hasta que uno dé esa salida. El algoritmo de password_hash es deliberadamente costoso, y eso es lo que lo vuelve útil para guardar contraseñas. Calcularlo una vez tarda unos milisegundos, que nadie nota al entrar al sistema; probar millones de candidatos tarda un tiempo que vuelve el ataque impracticable. Ese costo es un parámetro que se puede subir a medida que las computadoras se hacen más rápidas.

password_hash agrega además una sal: un valor al azar distinto para cada contraseña, que se guarda adentro del mismo resultado junto con el algoritmo usado y el costo. La sal hace que dos personas que eligieron la misma contraseña queden con hashes distintos, y deja sin efecto las tablas de hashes calculadas de antemano. password_verify lee de ahí la sal y el costo, recalcula con esos mismos parámetros y compara.

Tres momentos del guardado

// 1 · al crear el usuario: se guarda el resultado, nunca la contraseña
$hash = password_hash($clave, PASSWORD_DEFAULT);
// ... y $hash es lo que va a la columna `clave` de la tabla

// 2 · al entrar: se compara sin leer nada
if (password_verify($clave_tecleada, $fila['clave'])) {
  // la contraseña era la correcta
}

// 3 · nunca, en ningún momento
// $_SESSION['clave'] = $clave;      <- no se guarda
// echo $fila['clave'];              <- no se muestra
// error_log($clave);                <- no se registra
De dónde sale el VARCHAR(255)
Hoy PASSWORD_DEFAULT usa bcrypt, que produce 60 caracteres y empieza con $2y$. El manual de PHP advierte que ese algoritmo por omisión puede cambiar en versiones futuras, y un algoritmo distinto produce una salida más larga. La columna se define en 255 para que el sistema siga funcionando cuando eso pase, sin tener que migrar la tabla. Definirla en 60 funciona hoy y se rompe en silencio el día que cambie.

El resultado esperado. Cuatro cosas juntas: en la tabla la contraseña se ve como un texto largo que empieza con $2y$; se guarda con password_hash($clave, PASSWORD_DEFAULT); se comprueba con password_verify; y la columna es VARCHAR(255).

LA CONTRASENA EN LA TABLA

  tecleada          password_hash()        guardada
  "melina2026"  ─────────────────────►  "$2y$10$K9pQ..."
                                          60 caracteres

  guardada + tecleada  ──password_verify()──►  true / false

El síntoma. Tres formas distintas, con la misma raíz:

  • La contraseña se lee en la tabla. Está guardada tal cual se tecleó: quien abra la base tiene las contraseñas de todos. Y como la gente repite contraseñas, se lleva también las de otros lados.
  • Aparece md5 o sha1 en el código. Son de otra época y hoy se revierten con una búsqueda en internet.
  • La columna es corta, del estilo VARCHAR(20). El hash mide 60 caracteres: MySQL lo guarda cortado, password_verify compara contra un pedazo y el login nunca valida, sin un solo mensaje.

12. Guardia de acceso

Un login identifica a quien entra. Proteger las páginas es un paso aparte, y lo hace cada página preguntando por la sesión. La comprobación se escribe una vez, en un archivo, y se incluye arriba de todo lo que escribe en la base.

El motivo. El control de acceso se aplica en el punto donde ocurre la operación, y no en la puerta de entrada del sistema. La razón es la que vienen viendo desde el principio del día: cada pedido llega solo y por su cuenta, así que no hay ninguna «puerta» por la que todos tengan que pasar. Cualquier archivo .php del proyecto es una dirección alcanzable, y responde tanto si alguien llegó ahí desde el menú como si escribió la dirección. Por eso la comprobación se repite en cada archivo que modifica datos, incluidos los que procesan formularios y no muestran nada.

Cómo se devuelve un hallazgo
Se nombra la comprobación, se muestra el lugar y se dice qué pasaría. «En procesar_alta.php, línea 12, la consulta está armada por concatenación: un producto con apóstrofo la rompe.» No se toca el código del otro equipo, y no se dice si está bien o mal hecho el sistema — se señala una comprobación y su evidencia.

Encontrar en un sistema ajeno lo que se buscó en el propio es la prueba de que lo aprendido dejó de ser una lista de pasos y pasó a ser un criterio.
