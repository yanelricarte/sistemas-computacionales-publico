Antes de empezar

Trabajen los cuatro sobre la misma máquina: uno maneja y los demás leen. Cada comprobación dice qué abrir, qué tiene que pasar y qué corregir cuando pasa otra cosa. Al final de cada una hay una pregunta corta para responder entre todos antes de seguir.

Empiecen por las que fallan calladas
Las comprobaciones 1, 2, 5 y 9 tienen algo en común: el sistema sigue andando igual y el problema aparece más tarde. Ninguna da un mensaje de error, así que se buscan, no se esperan.

Para marcar lo importante: hacé doble clic sobre una palabra para resaltarla, o seleccioná una frase y tocá el botón que aparece al costado. Para sacar una marca, doble clic encima. Lo marcado queda guardado en este navegador.

Las preguntas dan tres intentos: si errás, se marca la opción, aparece una pista y seguís probando. La respuesta se muestra recién cuando se agotan.

1. La llave, fuera del repositorio

En GitHub. Entrá a tu repositorio en GitHub, desde el navegador, y buscá conexion.php (o como se llame el archivo donde están el usuario y la contraseña de MySQL). Mirar la carpeta de tu máquina no sirve: la pregunta es qué subiste.

El resultado esperado. El archivo no aparece en GitHub.

La corrección. Tres pasos, en este orden:

# 1) que Git deje de seguirlo de ahora en adelante
echo "conexion.php" >> .gitignore

# 2) sacarlo del repositorio sin borrarlo de tu maquina
git rm --cached conexion.php
git add .gitignore
git commit -m "La conexion sale del repositorio"
git push

# 3) cambiar la contrasena: lo que estuvo subido quedo en el historial

Para que un compañero sepa qué archivo le falta, subí un conexion-ejemplo.php con la forma y sin los datos reales.

El archivo de configuración y el .gitignore

Lo que están haciendo con conexion.php tiene un nombre y una convención. En casi todos los lenguajes ese archivo se llama .env —de environment, el entorno donde corre el sistema— y guarda lo que cambia de una máquina a otra: la dirección de la base, el usuario, la contraseña, las claves de los servicios que el sistema usa. Laravel, Node y Python trabajan así. En el PHP que escriben ustedes, conexion.php cumple exactamente ese papel.

La regla es siempre la misma, y tiene dos mitades:

  • El archivo con los valores no va al repositorio. Vive en cada máquina, con los datos de esa máquina.
  • Va un archivo de ejemplo, con las claves vacías. .env.example, o conexion-ejemplo.php. Quien clona el proyecto lo copia, le pone sus datos y arranca — sin ese ejemplo, no tiene forma de saber qué le falta.

El .gitignore es la lista de lo que Git deja afuera. Un proyecto web suele tener por lo menos esto:

.env
conexion.php

node_modules/
vendor/

.vscode/
Thumbs.db
node_modules, la carpeta que se regenera sola
Esa carpeta son las dependencias: código que escribió otra gente y que el proyecto usa. Se vuelve a bajar entera con un solo comando a partir de package.json, que sí va al repositorio, así que guardarla es de más: son decenas de miles de archivos que hacen lento cada clonado. Con vendor/ de PHP pasa lo mismo: se reconstruye desde composer.json.

El criterio que ordena las dos cosas: al repositorio va lo que ustedes escriben y lo que hace falta para reconstruir el resto. Queda afuera lo que se regenera solo, y lo que es secreto.

Escribilo. La línea del .gitignore que deja afuera la carpeta de dependencias de Node.

2. El juego de caracteres de la conexión

En conexion.php. Abrí tu conexion.php y buscá la línea mysqli_set_charset.

El resultado esperado. Está, justo después de conectar:

<?php
$conexion = mysqli_connect('localhost', 'root', '', 'tu_base');
mysqli_set_charset($conexion, 'utf8mb4');

La corrección. Agregala. Sin esa línea las tildes y las eñes salen rotas en el sitio aunque la base esté creada con utf8mb4_unicode_ci: la base guarda bien y el canal las trae mal. Se nota enseguida en el listado, que es la pantalla que va al documento.

La prueba: cargá un producto con tilde y miralo en la web.

Escribilo. La línea que va justo debajo de mysqli_connect en tu conexion.php.

3. Las consultas con datos que vienen de afuera

En los archivos del CRUD. Abrí los archivos que hacen INSERT, UPDATE, DELETE y el SELECT que busca por id. Mirá cómo se arma la consulta.

El resultado esperado. El dato viaja aparte de la consulta, con un signo de pregunta en su lugar.

La corrección. Vas a ver la variable pegada adentro del texto:

$sql = "INSERT INTO producto (nombre) VALUES ('$nombre')";   // asi no

Escrito así, lo que el visitante teclea se convierte en parte de la consulta. Un producto que se llame Detergente D'Oro ya rompe el INSERT por el apóstrofo; alguien que sepa lo que hace escribe un nombre que borra una tabla.

ANATOMIA DE LAS DOS FORMAS

  PEGADO                              PREPARADO
  "... VALUES ('$nombre')"            "... VALUES (?)"
   el dato ENTRA a la consulta         el dato viaja APARTE
   y puede cambiar lo que hace         y no cambia lo que hace

  1) prepare   el molde con los ?
  2) bind      los datos y su tipo     s texto   i entero   d decimal
  3) execute   la base los pone        en el lugar del ?, como DATOS

La prueba: cargá un producto con un apóstrofo en el nombre. Con la sentencia preparada se guarda entero; sin ella, salta un error de sintaxis de SQL.

Pregunta. Con una sentencia preparada, un producto llamado O'Higgins…

5. El motor de las tablas y la clave foránea

En phpMyAdmin. En phpMyAdmin, elegí tu base y mirá la columna Motor de la lista de tablas.

El resultado esperado. Dice InnoDB en las tablas que tienen clave foránea.

La corrección. Con MyISAM, el FOREIGN KEY que escribiste en el CREATE TABLE se acepta y se descarta en silencio. La relación queda escrita en el .sql y no existe en la base.

La prueba que decide: intentá borrar un rubro que tenga productos.

CON LA RELACION VIVA          SIN RELACION (MyISAM)

  ERROR 1451                    el rubro se borra
  Cannot delete or update       y los productos quedan
  a parent row: a foreign       apuntando a un id que
  key constraint fails          ya no existe

Corrección: Operaciones → Motor de almacenamiento → InnoDB, y volvé a declarar la clave foránea en Estructura → Vista de relaciones.

6. La comprobación del lado del servidor

En los archivos que procesan formularios. Los archivos que procesan un formulario, arriba de todo, antes del INSERT o del UPDATE.

El resultado esperado. Antes de tocar la base, PHP comprueba lo que llegó: que el campo esté, que el número sea un número, que el valor tenga sentido.

La corrección. El required y el maxlength del formulario son una ayuda para quien lo completa de buena fe. Se desactivan desde las herramientas del navegador en diez segundos, y también se saltean mandando el pedido sin pasar por tu página. La comprobación que gobierna es la de PHP, porque corre en el servidor y nadie la puede tocar.

El exit; que falta
Cada header('Location: ...') lleva un exit; en la línea siguiente. Sin él, PHP redirige y sigue ejecutando el archivo: la validación aparenta funcionar y la escritura se hace igual. Es una falla que no da ningún error.

Escribilo. La línea que va inmediatamente después de cada header('Location: …').

La comprobación completa arriba de un procesar_ — se abre con el código de la clase.

7. El id que viaja escondido

En el formulario de edición. El formulario de edición, el campo <input type="hidden" name="id">.

El resultado esperado. El archivo que procesa la edición comprueba que ese id sea un número y que la fila exista, antes de escribir.

La corrección. Escondido quiere decir que no se ve en la pantalla. Cualquiera que abra las herramientas del navegador cambia ese número y manda el formulario con otro id: edita una fila que nunca abrió.

$id = filter_input(INPUT_POST, 'id', FILTER_VALIDATE_INT);
if (!$id) {
  header('Location: listado.php?error=id');
  exit;
}

La pregunta que queda abierta —quién tiene permiso para mandar ese id— se resuelve en las secciones 11 y 12.

8. El enlace que borra

En el listado. El listado, el enlace o el botón de borrar.

El resultado esperado. El borrado sale de un formulario por POST, con una confirmación antes.

La corrección. Vas a ver algo así:

<a href="borrar.php?id=3">Borrar</a>

Escrito así, la dirección borrar.php?id=3 borra una fila con solo escribirla en la barra. Y como es un enlace común, lo puede pedir cualquier cosa que recorra la página sin intención de borrar nada.

Verdadero o falso. Con el borrado por POST, escribir borrar.php?id=3 en la barra de direcciones deja de borrar la fila.

9. Las contraseñas guardadas

En la tabla de usuarios y en el login. La tabla de usuarios en phpMyAdmin y el archivo que procesa el login.

El resultado esperado. Cuatro cosas juntas: en la tabla la contraseña se ve como un texto largo que empieza con $2y$; se guarda con password_hash($clave, PASSWORD_DEFAULT); se comprueba con password_verify; y la columna es VARCHAR(255).

LA CONTRASENA EN LA TABLA

  tecleada          password_hash()        guardada
  "melina2026"  ─────────────────────►  "$2y$10$K9pQ..."
                                          60 caracteres

  guardada + tecleada  ──password_verify()──►  true / false

  El camino de vuelta no existe: la contrasena no se lee en la tabla,
  tampoco la leen ustedes. Por eso "olvide mi contrasena" entrega una nueva.

La corrección. Tres formas distintas, con la misma raíz:

  • La contraseña se lee en la tabla. Está guardada tal cual se tecleó: quien abra la base tiene las contraseñas de todos. Y como la gente repite contraseñas, se lleva también las de otros lados.
  • Aparece md5 o sha1 en el código. Son de otra época y hoy se revierten con una búsqueda en internet.
  • La columna es corta, del estilo VARCHAR(20). El hash mide 60 caracteres: MySQL lo guarda cortado, password_verify compara contra un pedazo y el login nunca valida, sin un solo mensaje.

Pregunta. El login rechaza la contraseña correcta y no aparece ningún error. Lo primero que conviene mirar es…

10. Lo que ve el visitante cuando algo sale mal

En todo el código. Buscá mysqli_error y or die en tu código.

El resultado esperado. El visitante lee una frase común. El detalle técnico queda para ustedes.

La corrección. Lo más probable es que tengas esto:

mysqli_query($conexion, $sql) or die(mysqli_error($conexion));

Ese mensaje le muestra a cualquiera los nombres de tus tablas y de tus columnas, y a veces la ruta del archivo en el servidor. Es el primer lugar donde mira alguien que quiere entrar.

if (!mysqli_stmt_execute($sentencia)) {
  error_log(mysqli_error($conexion));
  header('Location: listado.php?error=guardar');
  exit;
}

Mientras desarrollan conviene ver el error completo. Lo que cambia es que el sistema quede así el día que lo muestran.

Verdadero o falso. Mientras desarrollan en su máquina conviene ver el mensaje de error completo de MySQL.

11. El login contra la base

Hasta acá el sistema hace bien lo que hace. Todavía no sabe quién lo está usando: escribir borrar.php?id=3 en la barra borra una fila, y nadie preguntó nada.

En la Clase 2 armaron un login con los usuarios escritos adentro del código, con un comentario que decía «esto se reemplaza por BD cuando entremos a MySQL». Hoy se cumple.

Primero, la tabla:

CREATE TABLE usuarios (
  id INT AUTO_INCREMENT PRIMARY KEY,
  usuario VARCHAR(50) NOT NULL UNIQUE,
  clave VARCHAR(255) NOT NULL,
  es_admin TINYINT(1) NOT NULL DEFAULT 0
) ENGINE=InnoDB;

Después, el hash del primer administrador. Una página de un solo uso, que se borra al terminar:

<?php echo password_hash('la-que-elijan', PASSWORD_DEFAULT); ?>

Copiás lo que sale a phpMyAdmin, como valor de clave. Tiene que empezar con $2y$ y medir 60 caracteres.

El mismo aviso para los dos errores
Cuando el login falla, el mensaje es igual si el usuario no existe y si la contraseña está mal. Distinguirlos le informa a quien prueba cuáles usuarios existen.

Pregunta. El login muestra el mismo aviso para «usuario inexistente» y para «contraseña equivocada» porque…

12. La guardia

Un login que entra y sale no protege nada por sí solo: las páginas tienen que preguntar. La comprobación se escribe una vez, en un archivo, y se incluye arriba de todo lo que escribe en la base.

LA GUARDIA

  alta.php    editar.php    borrar.php    procesar_*.php
      │            │             │              │
      └────────────┴─────────────┴──────────────┘
                 require 'guardia.php'
                          │
              hay $_SESSION['usuario'] ?
        si ──► sigue        no ──► login.php  +  exit;

  Esconder el enlace cambia lo que se ve.
  La guardia cambia lo que se puede hacer.

La prueba: cerrá la sesión y escribí la dirección de editar.php?id=1 a mano. Tiene que mandarte al login.

Identificado y autorizado son dos cosas
Quién sos lo resuelve el login. Qué podés hacer lo resuelve el rol: la columna es_admin guardada en la sesión, comprobada en las páginas de alta de artículos, rubros y marcas.

Pregunta. Pusiste la guardia en editar.php y no en procesar_edicion.php. Con eso…
