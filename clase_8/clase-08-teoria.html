0. De dónde venimos: la web y la base, por separado

En la Clase 7 tu base dejó de ser una tabla suelta y pasó a ser un modelo: dos tablas conectadas por una clave foránea.

  • CREATE TABLE con FOREIGN KEY — la relación declarada, con la FK del lado de los muchos.
  • INSERT en orden — primero la tabla apuntada, y en la FK el id, nunca el nombre.
  • SELECT ... WHERE director_id = ... — consultar filtrando por la clave foránea.
  • El error 1452 visto en vivo: la base se niega a guardar una fila que apunte a un id inexistente.

Eso está hecho y versionado. El paso que falta no es de SQL ni de diseño: es de comunicación. La base existe, y el sitio existe, pero todavía no se comunican. De eso trata esta clase.

1. El problema: los datos en dos lugares

En este momento tu proyecto tiene los datos en dos lugares, y entre ambos no hay comunicación:

  • En PHP: el sitio muestra la cartelera leyendo datos.php, un array escrito a mano desde la Clase 4.
  • En MySQL: la misma información, pero como filas reales, en las tablas que armaste en las Clases 5 y 7.
┌───────────────────┐      ┌────────────────────────┐
│ PHP (el sitio)     │      │ MySQL (los datos)      │
│ cartelera.php      │      │ cartelera              │
│  lee datos.php     │      │  peliculas · directores│
│  (array a mano)    │      │  filas reales          │
└─────────┬─────────┘      └──────────┬─────────────┘
          │            falta el canal │
          └────────────────╳──────────┘

¿Qué pasa si cambiás un dato en phpMyAdmin? La cartelera de la web no refleja el cambio. ¿Y si cambiás algo en datos.php? La base tampoco lo recibe. Son dos copias de la misma información que pueden desincronizarse, y cada corrección habría que hacerla dos veces.

La solución no es escribir los datos de nuevo en el programa: es abrir un canal entre los dos programas. PHP y MySQL son programas distintos, y este es el momento en que se conocen.

La idea de toda la clase
Los datos dejan de vivir adentro del programa y pasan a vivir en la base. La web los pide prestados (SELECT) y los devuelve (INSERT) a través de un puente llamado mysqli.

2. Conectar: los 4 datos y mysqli_connect

Para que tu programa entre a la base, PHP necesita saber dónde está esa base y con qué identidad entra. Son exactamente los cuatro datos que anotaste como tarea de la Clase 7:

host          localhost       en qué máquina vive la base
usuario       root            con qué usuario entra
contraseña    (vacía)         la clave de ese usuario
base          cartelera       cuál de las bases abre

Con esos cuatro datos, la función que abre el canal es mysqli_connect. Desarmala en partes:

$conexion = mysqli_connect( $host , $usuario , $clave , $base );
│           │              │         │         │      │
│           │              │         │         │      └─ 4) qué base abre
│           │              │         │         └─ 3) la contraseña de ese usuario
│           │              │         └─ 2) con qué usuario entra
│           │              └─ 1) dónde vive la base
│           └─ la función que abre el canal (familia mysqli)
└─ el resultado se guarda en $conexion: el canal listo para usar

mysqli no es una función suelta: es una familia de funciones con la que PHP habla con MySQL. Todas las que vamos a usar hoy empiezan con mysqli_ — es la señal de "esto es una conversación con la base".

mysqli_connect devuelve un valor. Si la conexión sale bien, devuelve el canal (un objeto conexión) y ese valor se guarda en $conexion. Si algo falla, devuelve false — y con false no se puede consultar nada, así que hay que enterarse antes de seguir.

El bloque completo, con el control del error:

<?php
// 1. Los cuatro datos, cada uno en una variable
$host      = 'localhost';
$usuario   = 'root';
$clave     = '';
$base      = 'cartelera';

// 2. Abrir el canal: el resultado queda en $conexion
$conexion = mysqli_connect($host, $usuario, $clave, $base);

// 3. ¿Se abrió bien? Si no, detenerse y decir el motivo
if (!$conexion) {
    die('Error de conexión: ' . mysqli_connect_error());
}
?>

Línea por línea:

  • El bloque 1 escribe los 4 datos una sola vez, arriba, para que se vean y se cambien fácil. Son las credenciales de tu base.
  • El bloque 2 llama a la función y guarda su resultado en $conexion.
  • El if (!$conexion): el ! es la negación. !$conexion lee "si no hay conexión". Cuando la función falló, devolvió false, y la condición se cumple.
  • die(...) detiene el programa en ese punto. No tiene sentido seguir si no hay canal: cualquier consulta fracasaría. Es un freno de emergencia que avisa.
  • mysqli_connect_error() devuelve el motivo del fallo, para no adivinar. Se concatena con el punto (.), como venís haciendo desde la Clase 1.
Qué es "localhost"
localhost no es internet: significa "esta misma computadora". Durante el desarrollo, la base vive en la misma máquina que el sitio. Cuando el proyecto se publique en un servidor real, ese dato va a ser la dirección de ese servidor — los otros tres conceptos no cambian.

3. conexion.php y el .gitignore

La conexión se escribe una sola vez

La conexión no se copia en cada página: se escribe una sola vez, en un archivo aparte, y se reutiliza. Es el mismo principio que aplicaste en la Clase 4 con datos.php: un solo lugar para el dato que se usa en muchos lados.

Dónde va el archivo: en la raíz del proyecto, junto a cartelera.php — lo viste en el mapa de §1. Ahí vive porque las páginas lo buscan en su misma carpeta.

C:/xampp/htdocs/cartelera/
├── cartelera.php           ← acá va:  <?php require 'conexion.php'; ?>
├── pelicula.php            ← y acá también
├── formulario.php
├── procesar_pelicula.php   ← (nuevo, §5)
├── datos.php
├── conexion.php            ← EL archivo nuevo: los 4 datos + el control del error
└── .gitignore              ← nuevo: dice "conexion.php no se sube"
conexion.php   (se crea una vez, se usa en todas las páginas)
───────────────────────────────────────────────────────────
<?php
// los 4 datos de TU base
$host      = 'localhost';
$usuario   = 'root';
$clave     = '';
$base      = 'cartelera';          // cambiá por el nombre de la tuya

$conexion = mysqli_connect($host, $usuario, $clave, $base);
if (!$conexion) {
    die('Error de conexión: ' . mysqli_connect_error());
}
?>

Cómo se trae a cada página: require

En cada página que toque la base, la conexión se incluye con require:

<?php require 'conexion.php'; ?>

¿Qué hace esa línea? Ejecuta el archivo conexion.php en ese mismo punto. El efecto es como si el contenido de conexion.php estuviera pegado ahí: después de esa línea, la variable $conexion ya está definida en la página y se puede usar.

Notá la diferencia con datos.php de la Clase 4: ese archivo devuelve un valor (return [ ... ]) que se captura con $peliculas = require 'datos.php'. conexion.php no devuelve nada con return: su código corre y deja la variable $conexion definida. Las dos formas sirven para separar código en un archivo aparte; lo que cambia es qué "entrega" el archivo.

¿Por qué en un archivo aparte? Si algún día cambia el nombre de la base, lo corregís en un lugar y todas las páginas quedan bien. Repetirlo en cada página significaría buscarlo y cambiarlo en todas — el problema que datos.php ya te resolvió en la Clase 4, ahora con las credenciales.

La regla: estos datos no se suben

Ese archivo contiene la llave de tu base: los datos con los que cualquiera puede entrar a leerla y modificarla. La regla que quedó anotada en la Clase 7 se implementa ahora.

La llave nunca se publica
Un repositorio en GitHub es visible para quien tenga el enlace, y lo que se sube queda ahí aunque después se borre. El archivo con los datos de acceso (conexion.php) no se sube nunca.

Para eso existe el .gitignore: un archivo de texto que se crea en la raíz del proyecto, donde se listan los archivos que Git no sube. Se llama "ignore" porque Git lo respeta a la hora de agregar archivos.

.gitignore   (en la raíz de tu proyecto, junto a conexion.php)
────────────────────────────────────────────
conexion.php       <- esta línea: "esto no se sube"
Cómo se recupera en otra computadora
Si conexion.php no se sube, ¿cómo lo volvés a tener en otra máquina? Queda una plantilla documentada en documentacion.md: los cuatro datos con espacios para completar. Cada computadora crea su conexion.php a partir de la plantilla. Lo que se comparte es la plantilla, nunca la llave.

4. Mostrar: la web lee la base

Con el canal abierto, el primer uso es leer. Compará estos dos listados:

// Clase 4: las filas estaban a mano en datos.php
$peliculas = [
    ['titulo' => 'Coco',         'anio' => 2017],
    ['titulo' => 'Intensamente', 'anio' => 2015]
];
foreach ($peliculas as $fila) {
    echo $fila['titulo'];
}

// Clase 8: las trae la base, mismo resto del listado
<?php require 'conexion.php'; ?>
<?php
$resultado = mysqli_query($conexion, 'SELECT * FROM peliculas');
while ($fila = mysqli_fetch_assoc($resultado)) {
    echo $fila['titulo'];
}
?>

La consulta tiene dos funciones, y conviene saber qué hace cada una:

  • mysqli_query($conexion, 'SELECT * FROM peliculas') — envía la consulta por el canal. El primer parámetro es por cuál canal viaja ($conexion); el segundo, el SQL, exactamente el que escribirías en phpMyAdmin. Devuelve el resultado: un "paquete" con las filas que respondieron. Si la consulta está mal escrita, devuelve false.
  • mysqli_fetch_assoc($resultado) — saca una fila por vez del paquete y la entrega como array asociativo. Cada llamada avanza a la fila siguiente; cuando no quedan más, devuelve null.

El while junta las dos: cada vuelta pregunta "¿queda una fila?" y, si hay, la imprime.

while ( $fila = mysqli_fetch_assoc($resultado) ) {
        │                        │
        │                        └─ saca la próxima fila como array
        │                           (o null si ya no quedan)
        └─ asigna esa fila a $fila y la usa como condición:
           si salió null, la condición es falsa y el while corta
}
La fila de la base es el array de la Clase 4
En datos.php escribías ['titulo' => 'Coco', 'anio' => 2017]. MySQL entrega exactamente lo mismo: $fila['titulo'], $fila['anio']. Las claves las pone la base, y son los nombres de las columnas del CREATE TABLE. No aprendés a listar de nuevo: aprendés de dónde salen las filas.

Cómo se integra en el HTML de la página

Las páginas de tu sitio no son solo PHP ni solo HTML: son los dos, mezclados. El patrón es abrir un bloque de PHP, usar HTML normal afuera y hacer que el echo escriba justo donde se lo llama. Es lo que reemplazás en la Parte 3 del TP.

<?php require 'conexion.php'; ?>                    ← 1. abrir el canal

<section class="cartelera">                           ← 2. HTML normal

  <?php                                             ← 3. abrir un bloque PHP
  $resultado = mysqli_query($conexion, 'SELECT * FROM peliculas');
  while ($fila = mysqli_fetch_assoc($resultado)) {
  ?>
    <article>                                       ← 4. el HTML de UNA película
      <h2><?php echo $fila['titulo']; ?></h2>
      <p>Estreno: <?php echo $fila['anio']; ?></p>
    </article>
  <?php } ?>                                         ← 5. cerrar bloque y bucle

</section>
  • Los bloques de PHP se abren con <?php y se cierran con ?>. Lo que queda entre esos dos marcadores se ejecuta; lo que queda afuera, se imprime tal cual.
  • El echo escribe el valor de la fila en ese mismo lugar del HTML: el navegador ve el resultado del echo como si fuera texto común.
  • El while repite todo el bloque de adentro — el <article> — una vez por fila. Una fila de la base se convierte en una tarjeta.
El PHP corre en el servidor; el navegador solo recibe HTML
Este código mezclado lo ejecuta Apache, en el servidor, no el navegador. El navegador recibe el resultado: HTML puro, sin rastro de <?php. Si apretás "Ver código fuente" (Ctrl+U) sobre tu cartelera, no vas a ver ninguna etiqueta PHP: vas a ver las tarjetas ya armadas, con los datos puestos.

Así se ve en el navegador. Cada vuelta del while produce una copia del <article> con los valores de una fila distinta. El navegador las apila una debajo de la otra:

┌──────────────────────────────────┐
│ Coco                             │
│ Estreno: 2017                    │
└──────────────────────────────────┘
┌──────────────────────────────────┐
│ Intensamente                     │
│ Estreno: 2015                    │
└──────────────────────────────────┘
  una tarjeta por cada fila que devolvió el SELECT

El mismo patrón se repite en el formulario de la Clase 8 (§6): ahí el echo no escribe el valor en un párrafo sino dentro de un atributo — value="<?php echo $d['id']; ?>". La idea es idéntica: el resultado del echo queda pegado en el HTML.

El SELECT es el mismo de la Clase 7: SELECT * FROM peliculas, o columnas puntuales, o WHERE para filtrar. Lo único nuevo es el viaje por el canal.

El límite que ahora se ve en pantalla

Cuando listás la cartelera, en la página aparece esto:

Intensamente · 2015 · director_id = 3    ← un número, no un nombre

Y lo que querrías ver es "Pete Docter". Es el mismo límite de la Clase 7, ahora en la web: mostrar una tabla muestra la FK como número. Cruzar las dos tablas en una sola consulta se resuelve con JOIN, y se aborda cuando el listado lo pida.

Ampliación: las dos tablas en una sola consulta
Ejecutá esta sentencia y observá el resultado: 
SELECT peliculas.titulo, directores.nombre
FROM peliculas
JOIN directores ON peliculas.director_id = directores.id;
Leída en castellano: "traé el título de peliculas y el nombre de directores, uniendo aquellas filas donde el director_id coincide con el id".

5. Agregar: INSERT desde la web

El segundo uso del canal es escribir. Hasta ahora, cargar una película nueva significaba abrir phpMyAdmin y ejecutar un INSERT a mano. Ahora eso lo hace un formulario del sitio.

El recorrido completo ya lo conocés por partes:

formulario  ──POST──►  procesar_pelicula.php  ──INSERT──►  la base
titulo                        │                            │
anio                         │                            │
director_id                  │   (la fila nueva)          ▼
                             └── header('Location:')      el listado la muestra
  • El formulario y el POST — de la Clase 1.
  • La redirección header('Location:') — de la Clase 2.
  • El INSERT — de la Clase 5.

Lo nuevo es cómo se escribe ese INSERT desde PHP. Y acá hay una regla que no se negocia.

La regla: el dato del usuario nunca va dentro de la consulta

La tentación es armar el SQL pegando el dato entre comillas: 'INSERT ... VALUES ("' . $_POST['titulo'] . '")'. Eso es un error, y conviene ver por qué antes de que aparezca solo.

Si el título es ¿Qué pasó ayer?, el apóstrofo rompe la consulta: para SQL, el apóstrofo es la marca de fin de texto, así que el texto se corta en la mitad y sobra basura que no entiende.

El caso más grave es otro: quien escribe en el formulario podría escribir SQL en vez de un título, y esa consulta correría tal cual. Ese ataque tiene nombre — inyección SQL — y se previene con una sola práctica, desde el principio.

La forma correcta usa una sentencia preparada. La clave no está en el SQL: está en cómo viaja. En vez de armar una sola consulta con el dato adentro, la consulta viaja en dos partes separadas:

┌────────────────────────────── VIAJE 1: el molde ──────────────────────────────┐
│                                                                                │
│   INSERT INTO peliculas (titulo, anio, director_id) VALUES (?, ?, ?)          │
│                                                                                │
│   cada ? es un lugar vacío: ahí van a entrar los datos, en el viaje 2         │
└────────────────────────────────────────────────────────────────────────────────┘

┌────────────────────────────── VIAJE 2: los valores ───────────────────────────┐
│                                                                                │
│   $titulo = "Coco"     $anio = 2017     $director_id = 2                      │
│                                                                                │
│   llegan como DATOS: se leen, nunca se ejecutan como instrucción              │
└────────────────────────────────────────────────────────────────────────────────┘

Es como una planilla de inscripción en papel: el texto impreso es fijo y tiene espacios en blanco; después se llenan con los datos. Lo que se escribe en los espacios no se interpreta como parte del texto impreso — queda como dato. Eso mismo hace la sentencia preparada con el SQL.

En código, son tres pasos:

// 1) PREPARAR — viaje 1: enviar el molde
$stmt = mysqli_prepare($conexion,
    'INSERT INTO peliculas (titulo, anio, director_id) VALUES (?, ?, ?)');

// 2) ATAR — dejar listos los datos para el viaje 2, con su tipo
//    s = texto (string) · i = entero (integer)
mysqli_stmt_bind_param($stmt, 'sii', $titulo, $anio, $director_id);

// 3) EJECUTAR — viaje 2: enviar los valores y guardar la fila
mysqli_stmt_execute($stmt);

Paso a paso:

  • 1) mysqli_prepare envía el molde por el canal. MySQL lo recibe, lo interpreta como instrucción (qué se va a guardar y en qué columnas) y devuelve la "consulta armada", que se guarda en $stmt. Todavía no se guardó ninguna fila.
  • 2) mysqli_stmt_bind_param ata cada dato a su lugar, en orden: el primero a titulo, el segundo a anio, el tercero a director_id. 'sii' le dice a PHP el tipo de cada uno para que los entregue bien: s = texto, i = número entero. Un año viaja como número (2017), no como texto ("2017").
  • 3) mysqli_stmt_execute hace el viaje 2: envía los valores y recién ahí MySQL guarda la fila.

¿Por qué esto neutraliza el apóstrofo y la inyección? Porque el dato viaja solo, después del molde, y MySQL lo trata como dato. El apóstrofo de ¿Qué pasó ayer? ya no puede cerrar un texto de SQL: no se escribió dentro del molde, llega como un carácter más del valor "¿Qué pasó ayer?". Y si en el formulario escribieran SQL, ese texto llegaría en el viaje 2 y MySQL lo guardaría literalmente como dato — nunca lo ejecuta, porque la instrucción ya se interpretó en el viaje 1.

Cuándo se usa cada una
Toda consulta que lleve datos del formulario se escribe con sentencia preparada. mysqli_query queda para las consultas sin datos del usuario — sobre todo los SELECT, que solo leen.

La integridad referencial viaja con el INSERT

Todo lo que aprendiste en la Clase 7 sigue vigente. Si el formulario envía un director_id que no existe en directores, la base rechaza la fila:

ERROR 1452: Cannot add or update a child row:
a foreign key constraint fails

Es el mismo error que provocaste en la Clase 7, ahora llegando desde la web. La regla que declaraste en el CREATE TABLE sigue trabajando; lo único que cambió es quién la dispara.

6. La clave foránea en el formulario

En el formulario de alta hay un campo que no es de texto: la clave foránea. Que el usuario escriba el número a mano provocaría el error de la Clase 7 — "¿cuál era el id de Pete Docter?"

La solución es un menú desplegable que se llena desde la base:

<form method="POST" action="procesar_pelicula.php">
  <label>Título: <input type="text" name="titulo" required></label>
  <label>Año: <input type="number" name="anio"></label>
  <label>Director:
    <select name="director_id">
      <?php
      $resultado = mysqli_query($conexion,
          'SELECT id, nombre FROM directores ORDER BY nombre');
      while ($d = mysqli_fetch_assoc($resultado)) {
      ?>
        <option value="<?php echo $d['id']; ?>">
          <?php echo $d['nombre']; ?>
        </option>
      <?php } ?>
    </select>
  </label>
  <button>Guardar</button>
</form>

Dentro del menú se escribe un pequeño listado — el mismo que aprendiste en §4, con un SELECT propio:

  • El SELECT trae dos columnas: id (lo que se envía) y nombre (lo que se ve). El ORDER BY nombre ordena el menú alfabéticamente.
  • Cada <option> tiene un value (el id) y un texto visible (el nombre).
El menú muestra nombres y envía ids
Lo que el usuario ve es Lee Unkrich; lo que se envía es el value, que es el id. Es la decisión de la Clase 7 aplicada en la web: en la FK va el número, nunca el nombre. El menú es la garantía de que nadie tenga que adivinarlo.

Glosario

TérminoQué significa
mysqliLa familia de funciones de PHP para hablar con MySQL. Todas las de esta clase empiezan con mysqli_.
ConexiónEl canal entre PHP y MySQL que abre mysqli_connect. Sin el canal, ninguna consulta viaja.
HostDónde vive la base. En desarrollo es localhost; en producción, la dirección del servidor.
requireInstrucción de PHP que ejecuta otro archivo en ese punto. La conexión se incluye así en cada página.
die()Detiene el programa y muestra un mensaje. Se usa para no seguir sin conexión.
mysqli_queryEnvía una consulta SQL por el canal y devuelve el resultado (o false si la consulta está mal).
ResultadoEl "paquete" de filas que devuelve mysqli_query. Se recorre con mysqli_fetch_assoc.
mysqli_fetch_assocDevuelve una fila del resultado como array asociativo (claves = columnas), avanzando una fila por llamada.
Sentencia preparadaUna consulta con lugares reservados (?) a la que el dato se entrega por separado, después. Previene la inyección SQL.
bind_paramLa parte de la sentencia preparada que ata cada dato a su lugar, indicando el tipo (s texto, i entero).
Inyección SQLEscribir SQL dentro de un campo del formulario para que la consulta haga otra cosa. Se previene no concatenando datos en la consulta.
.gitignoreArchivo donde se listan los archivos que Git no sube al repositorio.
Integridad referencialLa garantía de que toda clave foránea apunta a una fila que existe. La hace cumplir MySQL.

7. Próximos pasos

Con esta clase se abre la Etapa 3 del proyecto: PHP y MySQL conectados. Hoy hiciste las dos operaciones que arrancan el CRUD:

  • Crear (C): el formulario que inserta una fila — el INSERT de hoy.
  • Leer (R): el listado que muestra las filas de la base — el SELECT de hoy.

Quedan dos operaciones, y ambas se resuelven con la misma base que ya tenés:

  • Actualizar (U): cuando una fila ya cargada tiene un dato mal, la web debería poder modificarla (UPDATE) desde un formulario precargado.
  • Borrar (D): poder eliminar una fila (DELETE) desde el sitio.

Con esas dos, el sistema queda completo: eso se llama CRUD, y es la base de casi todas las aplicaciones web.
