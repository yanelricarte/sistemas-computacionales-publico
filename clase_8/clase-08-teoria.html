0. Web y base, por separado

En la Clase 7 su base dejó de ser una tabla suelta y pasó a ser un modelo: dos tablas conectadas por una clave foránea.

  • CREATE TABLE con FOREIGN KEY — la relación declarada, con la FK del lado de los muchos.
  • INSERT en orden — primero la tabla apuntada, y en la FK el id, nunca el nombre.
  • SELECT ... WHERE director_id = ... — consultar filtrando por la clave foránea.
  • El error 1452 visto en vivo: la base se niega a guardar una fila que apunte a un id inexistente.

1. Datos en dos lugares

En este momento su proyecto tiene los datos en dos lugares, y entre ambos no hay comunicación:

  • En PHP: el sitio muestra la cartelera leyendo datos.php, un array escrito a mano desde la Clase 4.
  • En MySQL: la misma información, pero como filas reales, en las tablas que armaron en las Clases 5 y 7.
┌───────────────────┐      ┌────────────────────────┐
│ PHP (el sitio)    │      │ MySQL (los datos)      │
│ cartelera.php     │      │ cartelera              │
│  lee datos.php    │      │  peliculas · directores│
│  (array a mano)   │      │  filas reales          │
└─────────┬─────────┘      └──────────┬─────────────┘
          │            falta el canal │
          └────────────────╳──────────┘

¿Qué pasa si cambian un dato en phpMyAdmin? La cartelera de la web no refleja el cambio. ¿Y si cambian algo en datos.php? La base tampoco lo recibe. Son dos copias de la misma información que pueden desincronizarse, y cada corrección habría que hacerla dos veces.

La solución es abrir un canal entre los dos programas, para que el sitio le pida los datos a la base cada vez que los necesita. PHP y MySQL son programas distintos, y este es el momento en que se conocen.

La idea de toda la clase
Los datos dejan de vivir adentro del programa y pasan a vivir en la base. La web los pide prestados (SELECT) y los devuelve (INSERT) a través de un puente llamado mysqli.

2. Cuatro datos y mysqli_connect

Para que su programa entre a la base, PHP necesita saber dónde está esa base y con qué identidad entra. Son los datos que anotaste como tarea de la Clase 7 —host, usuario y contraseña—, más el nombre de su base:

host          localhost       en qué máquina vive la base
usuario       root            con qué usuario entra
contraseña    (vacía)         la clave de ese usuario
base          cartelera       cuál de las bases abre

Con esos cuatro datos, la función que abre el canal es mysqli_connect. Desarmala en partes:

$conexion = mysqli_connect( $host , $usuario , $clave , $base );
│           │              │         │         │      │
│           │              │         │         │      └─ 4) qué base abre
│           │              │         │         └─ 3) la contraseña de ese usuario
│           │              │         └─ 2) con qué usuario entra
│           │              └─ 1) dónde vive la base
│           └─ la función que abre el canal (familia mysqli)
└─ el resultado se guarda en $conexion: el canal listo para usar

mysqli es una familia de funciones, la que PHP usa para hablar con MySQL. Todas las de esta clase empiezan con mysqli_, y ese prefijo es la señal de que ahí hay una conversación con la base.

mysqli_connect devuelve un valor. Si la conexión sale bien, devuelve el canal (un objeto conexión) y ese valor se guarda en $conexion. Si algo falla, devuelve false — y con false no se puede consultar nada, así que hay que enterarse antes de seguir.

El bloque completo, con el control del error:

<?php
// 1. Los errores de la base los manejamos nosotros, acá abajo
mysqli_report(MYSQLI_REPORT_OFF);

// 2. Los cuatro datos, cada uno en una variable
$host      = 'localhost';
$usuario   = 'root';
$clave     = '';
$base      = 'cartelera';

// 3. Abrir el canal: el resultado queda en $conexion
$conexion = mysqli_connect($host, $usuario, $clave, $base);

// 4. ¿Se abrió bien? Si no, detenerse y decir el motivo
if (!$conexion) {
    die('Error de conexión: ' . mysqli_connect_error());
}
?>

Línea por línea:

  • mysqli_report(MYSQLI_REPORT_OFF) le pide a PHP que, ante un problema con la base, devuelva el error en vez de cortar el programa con un mensaje propio. Va primero, una sola vez, y es lo que hace que el aviso que escribimos en el punto 4 sea el que se vea en pantalla.
  • El bloque 2 escribe los 4 datos una sola vez, arriba, para que se vean y se cambien fácil. Son las credenciales de su base.
  • El bloque 3 llama a la función y guarda su resultado en $conexion.
  • El if (!$conexion): el ! es la negación. !$conexion lee "si no hay conexión". Cuando la función falló, devolvió false, y la condición se cumple.
  • die(...) detiene el programa en ese punto. Sin canal, cualquier consulta que viniera después fracasaría, así que conviene frenar acá y avisar el motivo.
  • mysqli_connect_error() devuelve el motivo del fallo, para no adivinar. Se concatena con el punto (.), como vienen haciendo desde la Clase 1.
Qué es "localhost"
localhost no es internet: significa "esta misma computadora". Durante el desarrollo, la base vive en la misma máquina que el sitio. Cuando el proyecto se publique en un servidor real, ese dato va a ser la dirección de ese servidor — los otros tres conceptos no cambian.

3. conexion.php y .gitignore

La conexión se escribe una sola vez

La conexión se escribe una sola vez, en un archivo aparte, y desde ahí se reutiliza en todas las páginas. Es el mismo principio que aplicaste en la Clase 4 con datos.php: un solo lugar para el dato que se usa en muchos lados.

Dónde va el archivo: en la raíz del proyecto, junto a cartelera.php — lo vieron en el mapa de §1. Ahí vive porque las páginas lo buscan en su misma carpeta.

C:/xampp/htdocs/cartelera/
├── cartelera.php           ← acá va:  <?php require 'conexion.php'; ?>
├── pelicula.php            ← y acá también
├── formulario.php          ← y acá: el menú de la FK consulta la base (§6)
├── procesar_pelicula.php   ← (nuevo, §5) también lo necesita
├── datos.php
├── conexion.php            ← EL archivo nuevo: los 4 datos + el control del error
└── .gitignore              ← nuevo: dice "conexion.php no se sube"
conexion.php   (se crea una vez, se usa en todas las páginas)
───────────────────────────────────────────────────────────
<?php
mysqli_report(MYSQLI_REPORT_OFF);  // los errores los manejamos acá abajo

// los 4 datos de LA base del equipo
$host      = 'localhost';
$usuario   = 'root';
$clave     = '';
$base      = 'cartelera';          // cambiá por el nombre de la tuya

$conexion = mysqli_connect($host, $usuario, $clave, $base);
if (!$conexion) {
    die('Error de conexión: ' . mysqli_connect_error());
}
?>

Inclusión en cada página con require

En cada página que toque la base, la conexión se incluye con require:

<?php require 'conexion.php'; ?>

¿Qué hace esa línea? Ejecuta el archivo conexion.php en ese mismo punto. El efecto es como si el contenido de conexion.php estuviera pegado ahí: después de esa línea, la variable $conexion ya está definida en la página y se puede usar.

Notá la diferencia con datos.php de la Clase 4: ese archivo devuelve un valor (return [ ... ]) que se captura con $peliculas = require 'datos.php'. conexion.php no devuelve nada con return: su código corre y deja la variable $conexion definida. Las dos formas sirven para separar código en un archivo aparte; lo que cambia es qué "entrega" el archivo.

¿Por qué en un archivo aparte? Si algún día cambia el nombre de la base, lo corrigen en un lugar y todas las páginas quedan bien. Repetirlo en cada página significaría buscarlo y cambiarlo en todas — el problema que datos.php ya te resolvió en la Clase 4, ahora con las credenciales.

La regla: estos datos no se suben

Ese archivo contiene la llave de su base: los datos con los que cualquiera puede entrar a leerla y modificarla. La regla que quedó anotada en la Clase 7 se implementa ahora.

La llave nunca se publica
Un repositorio en GitHub es visible para quien tenga el enlace, y lo que se sube queda ahí aunque después se borre. El archivo con los datos de acceso (conexion.php) no se sube nunca.

Para eso existe el .gitignore: un archivo de texto que se crea en la raíz del proyecto, donde se listan los archivos que Git no sube. Se llama "ignore" porque Git lo respeta a la hora de agregar archivos.

.gitignore   (en la raiz del proyecto, junto a conexion.php)
────────────────────────────────────────────
conexion.php       <- esta línea: "esto no se sube"
Cómo se recupera en otra computadora
Si conexion.php no se sube, ¿cómo lo vuelven a tener en otra máquina? Queda una plantilla documentada en documentacion.md: los cuatro datos con espacios para completar. Cada computadora crea su conexion.php a partir de la plantilla. Lo que se comparte es la plantilla, nunca la llave.

4. Lectura de la base desde el sitio

Con el canal abierto, el primer uso es leer. Comparen estos dos listados:

// Clase 4: las filas estaban a mano en datos.php
$peliculas = [
    ['titulo' => 'Coco',         'anio' => 2017],
    ['titulo' => 'Intensamente', 'anio' => 2015]
];
foreach ($peliculas as $fila) {
    echo $fila['titulo'];
}

// Clase 8: las trae la base, mismo resto del listado
<?php require 'conexion.php'; ?>
<?php
$resultado = mysqli_query($conexion, 'SELECT * FROM peliculas');
while ($fila = mysqli_fetch_assoc($resultado)) {
    echo $fila['titulo'];
}
?>

La consulta tiene dos funciones, y conviene saber qué hace cada una:

  • mysqli_query($conexion, 'SELECT * FROM peliculas') — envía la consulta por el canal. El primer parámetro es por cuál canal viaja ($conexion); el segundo, el SQL, exactamente el que escribirías en phpMyAdmin. Devuelve el resultado: un "paquete" con las filas que respondieron. Si la consulta está mal escrita, devuelve false.
  • mysqli_fetch_assoc($resultado) — saca una fila por vez del paquete y la entrega como array asociativo. Cada llamada avanza a la fila siguiente; cuando no quedan más, devuelve null.

El while junta las dos: cada vuelta pregunta "¿queda una fila?" y, si hay, la imprime.

while ( $fila = mysqli_fetch_assoc($resultado) ) {
        │                        │
        │                        └─ saca la próxima fila como array
        │                           (o null si ya no quedan)
        └─ asigna esa fila a $fila y la usa como condición:
           si salió null, la condición es falsa y el while corta
}
La fila de la base es el array de la Clase 4
En datos.php escribías ['titulo' => 'Coco', 'anio' => 2017]. MySQL entrega exactamente lo mismo: $fila['titulo'], $fila['anio']. Las claves las pone la base, y son los nombres de las columnas del CREATE TABLE. Lo que se aprende acá es de dónde salen las filas; listar ya lo sabías.

Integración en el HTML de la página

Las páginas de su sitio combinan PHP y HTML en el mismo archivo. El patrón es abrir un bloque de PHP, usar HTML normal afuera y hacer que el echo escriba justo donde se lo llama. Es lo que reemplazan en la Parte 3 del TP.

<?php require 'conexion.php'; ?>                    ← 1. abrir el canal

<section class="cartelera">                           ← 2. HTML normal

  <?php                                             ← 3. abrir un bloque PHP
  $resultado = mysqli_query($conexion, 'SELECT * FROM peliculas');
  while ($fila = mysqli_fetch_assoc($resultado)) {
  ?>
    <article>                                       ← 4. el HTML de UNA película
      <h2><?php echo $fila['titulo']; ?></h2>
      <p>Estreno: <?php echo $fila['anio']; ?></p>
    </article>
  <?php } ?>                                         ← 5. cerrar bloque y bucle

</section>
  • Los bloques de PHP se abren con <?php y se cierran con ?>. Lo que queda entre esos dos marcadores se ejecuta; lo que queda afuera, se imprime tal cual.
  • El echo escribe el valor de la fila en ese mismo lugar del HTML: el navegador ve el resultado del echo como si fuera texto común.
  • El while repite todo el bloque de adentro — el <article> — una vez por fila. Una fila de la base se convierte en una tarjeta.
El PHP corre en el servidor; el navegador solo recibe HTML
Este código mezclado lo ejecuta Apache, en el servidor, no el navegador. El navegador recibe el resultado: HTML puro, sin rastro de <?php. Si aprietan "Ver código fuente" (Ctrl+U) sobre su cartelera, no van a ver ninguna etiqueta PHP: van a ver las tarjetas ya armadas, con los datos puestos.

Así se ve en el navegador. Cada vuelta del while produce una copia del <article> con los valores de una fila distinta. El navegador las apila una debajo de la otra:

┌──────────────────────────────────┐
│ Coco                             │
│ Estreno: 2017                    │
└──────────────────────────────────┘
┌──────────────────────────────────┐
│ Intensamente                     │
│ Estreno: 2015                    │
└──────────────────────────────────┘
  una tarjeta por cada fila que devolvió el SELECT

El mismo patrón se repite en el formulario de la Clase 8 (§6): ahí el echo no escribe el valor en un párrafo sino dentro de un atributo — value="<?php echo $d['id']; ?>". La idea es idéntica: el resultado del echo queda pegado en el HTML.

El SELECT es el mismo de la Clase 7: SELECT * FROM peliculas, o columnas puntuales, o WHERE para filtrar. Lo único nuevo es el viaje por el canal.

El límite que ahora se ve en pantalla

Cuando listan la cartelera, en la página aparece esto:

Intensamente · 2015 · director_id = 3    ← un número, no un nombre

Y lo que querrías ver es "Pete Docter". Es el mismo límite de la Clase 7, ahora en la web: mostrar una tabla muestra la FK como número. Cruzar las dos tablas en una sola consulta se resuelve con JOIN, y se aborda cuando el listado lo pida.

Ampliación: las dos tablas en una sola consulta
Ejecuten esta sentencia y observá el resultado: 
SELECT peliculas.titulo, directores.nombre
FROM peliculas
JOIN directores ON peliculas.director_id = directores.id;
Leída en castellano: "traé el título de peliculas y el nombre de directores, uniendo aquellas filas donde el director_id coincide con el id".

5. INSERT desde la web

El segundo uso del canal es escribir. Hasta ahora, cargar una película nueva significaba abrir phpMyAdmin y ejecutar un INSERT a mano. Ahora eso lo hace un formulario del sitio.

El recorrido completo ya lo conocen por partes:

formulario  ──POST──►  procesar_pelicula.php  ──INSERT──►  la base
titulo                           │                           │
anio                             │   (la fila nueva)         │
director_id                      │                           ▼
                                 └── header('Location:')      el listado la muestra
  • El formulario y el POST — de la Clase 1.
  • La redirección header('Location:') — de la Clase 2.
  • El INSERT — de la Clase 5.

La redirección del final cumple una función concreta. Si la página del procesador se quedara mostrando "listo", cada F5 volvería a enviar el formulario y guardaría la fila otra vez. Al redirigir, lo que queda cargado en el navegador es el listado, y recargar un listado solo vuelve a leer.

Lo nuevo es cómo se escribe ese INSERT desde PHP. Y acá hay una regla que no se negocia.

La regla: el dato del usuario nunca va dentro de la consulta

La tentación es armar el SQL pegando el dato entre comillas: "INSERT ... VALUES ('" . $_POST['titulo'] . "')". Eso es un error, y conviene ver por qué antes de que aparezca solo.

Si el título es Ocean's Eleven, el apóstrofo rompe la consulta: para SQL, el apóstrofo es la marca de fin de texto, así que la consulta que llega es VALUES ('Ocean' más un s Eleven') suelto que no entiende. Es un título real y alcanza para romperla.

El caso más grave es otro: quien escribe en el formulario podría escribir SQL en vez de un título, y esa consulta correría tal cual. Ese ataque tiene nombre — inyección SQL — y se previene con una sola práctica, desde el principio.

La forma correcta usa una sentencia preparada. Lo que cambia está en cómo viaja la consulta. En vez de armar una sola consulta con el dato adentro, la consulta viaja en dos partes separadas:

┌─────────────────────────── VIAJE 1: el molde ────────────────────────────┐
│                                                                          │
│   INSERT INTO peliculas (titulo, anio, director_id) VALUES (?, ?, ?)     │
│                                                                          │
│   cada ? es un lugar vacío: ahí van a entrar los datos, en el viaje 2    │
└──────────────────────────────────────────────────────────────────────────┘

┌────────────────────────── VIAJE 2: los valores ──────────────────────────┐
│                                                                          │
│   $titulo = "Ocean's Eleven"     $anio = 2001     $director_id = 2       │
│                                                                          │
│   llegan como DATOS: se leen, nunca se ejecutan como instrucción         │
└──────────────────────────────────────────────────────────────────────────┘

Es como una planilla de inscripción en papel: el texto impreso es fijo y tiene espacios en blanco; después se llenan con los datos. Lo que se escribe en los espacios no se interpreta como parte del texto impreso — queda como dato. Eso mismo hace la sentencia preparada con el SQL.

En código, son tres pasos:

// 1) PREPARAR — viaje 1: enviar el molde
$stmt = mysqli_prepare($conexion,
    'INSERT INTO peliculas (titulo, anio, director_id) VALUES (?, ?, ?)');

// 2) ATAR — dejar listos los datos para el viaje 2, con su tipo
//    s = texto (string) · i = entero (integer)
mysqli_stmt_bind_param($stmt, 'sii', $titulo, $anio, $director_id);

// 3) EJECUTAR — viaje 2: enviar los valores y guardar la fila
mysqli_stmt_execute($stmt);

Paso a paso:

  • 1) mysqli_prepare envía el molde por el canal. MySQL lo recibe, lo interpreta como instrucción (qué se va a guardar y en qué columnas) y devuelve la "consulta armada", que se guarda en $stmt. Todavía no se guardó ninguna fila.
  • 2) mysqli_stmt_bind_param ata cada dato a su lugar, en orden: el primero a titulo, el segundo a anio, el tercero a director_id. 'sii' le dice a PHP el tipo de cada uno para que los entregue bien: s = texto, i = número entero. Un año viaja como número (2017), no como texto ("2017").
  • 3) mysqli_stmt_execute hace el viaje 2: envía los valores y recién ahí MySQL guarda la fila.

¿Por qué esto neutraliza el apóstrofo y la inyección? Porque el dato viaja solo, después del molde, y MySQL lo trata como dato. El apóstrofo de Ocean's Eleven ya no puede cerrar un texto de SQL: no se escribió dentro del molde, llega como un carácter más del valor "Ocean's Eleven". Y si en el formulario escribieran SQL, ese texto llegaría en el viaje 2 y MySQL lo guardaría literalmente como dato — nunca lo ejecuta, porque la instrucción ya se interpretó en el viaje 1.

Cuándo se usa cada una
Toda consulta que lleve datos del formulario se escribe con sentencia preparada. mysqli_query queda para las consultas sin datos del usuario — sobre todo los SELECT, que solo leen.

La integridad referencial viaja con el INSERT

Todo lo que aprendiste en la Clase 7 sigue vigente. Si el formulario envía un director_id que no existe en directores, la base rechaza la fila.

Para enterarte cuando eso pasa, el execute se controla igual que la conexión: si devuelve false, la fila no se guardó y hay que decirlo. Sin este control, la página redirigiría al listado como si todo hubiera salido bien, y la fila simplemente no estaría.

if (!mysqli_stmt_execute($stmt)) {
    die('No se pudo guardar: ' . mysqli_stmt_error($stmt));
}

El mensaje que aparece es el conocido:

No se pudo guardar: Cannot add or update a child row:
a foreign key constraint fails

Es el mismo error que provocaste en la Clase 7, ahora llegando desde la web. La regla que declaraste en el CREATE TABLE sigue trabajando; lo único que cambió es quién la dispara.

Sentencias preparadas

Las cuatro operaciones del bloque 1 tienen algo en común: todas reciben un dato que escribió otra persona. El nombre de un producto, un precio, el id de la fila que se edita. De cómo ese dato llega a la consulta depende que el sistema sea sólido o que se pueda romper desde un formulario.

Una consulta armada pegando variables llega a la base como una sola cadena, y el analizador la lee entera para decidir qué operación ejecutar. Ahí el texto de quien escribe queda mezclado con las palabras de la orden. Un apóstrofo en un nombre cambia la estructura de la consulta, y alguien que sepa lo que hace escribe algo peor. Eso es la inyección SQL.

Una sentencia preparada separa el proceso en dos etapas. Primero manda la consulta con signos de pregunta en el lugar de los valores, y la base la analiza y planifica ahí, sin los datos. Después manda los valores, que se acoplan a un plan ya decidido y no se vuelven a analizar como SQL.

// los tres pasos, iguales para las cuatro operaciones
$sql = "INSERT INTO producto (nombre, precio) VALUES (?, ?)";
$sentencia = mysqli_prepare($conexion, $sql);        // 1 · el molde
mysqli_stmt_bind_param($sentencia, 'sd', $nombre, $precio);  // 2 · los datos y su tipo
mysqli_stmt_execute($sentencia);                     // 3 · ejecutar

// tipos:  s texto   ·   i entero   ·   d con decimales
// la cadena tiene una letra por cada ?, en el mismo orden
El id también viene de afuera
En un UPDATE y en un DELETE, el id del WHERE llega desde el formulario o desde la dirección igual que el nombre. También va con ?, y en bind_param queda último, porque ese es el orden de los signos de pregunta.

Contraseñas y hash

El login del sistema compara una contraseña. La pregunta es qué guarda la base para poder comparar.

Importancia

Una tabla de usuarios con las contraseñas escritas tal cual se tecleó es un problema que excede al sistema. Quien llegue a esa tabla se lleva las contraseñas de personas reales, y como casi todo el mundo repite la misma en varios lugares, con esa lista también entra a sus correos. No alcanza con que la tabla sea difícil de alcanzar: hay que guardar de manera que, aunque alguien la lea, no le sirva.

Cifrar y hashear, dos cosas distintas

Las dos palabras se usan como sinónimos y nombran cosas diferentes. Cifrar sirve para guardar algo que después hay que volver a leer, y por eso tiene vuelta atrás con una clave. Hashear sirve para comprobar algo que nunca hace falta volver a leer, y no tiene vuelta atrás: no existe ninguna clave que lo deshaga.

Una contraseña nunca hace falta volver a leerla. Al entrar, el sistema no compara la contraseña guardada con la tecleada: vuelve a calcular el hash de la tecleada y compara los dos resultados. Por eso se hashea y no se cifra, y por eso los sitios serios mandan una contraseña nueva en lugar de la vieja.

Funciones de hash

Toma un texto de cualquier largo y devuelve una salida de largo fijo. La misma entrada da siempre la misma salida, así que sirve para comparar. Cambiar una letra cambia toda la salida, así que mirar el hash no acerca a la contraseña. Y para el camino inverso no hay cálculo: la única vía es probar textos hasta que uno dé esa salida.

Ahí está la decisión de diseño de password_hash: el algoritmo es deliberadamente costoso. Calcularlo una vez tarda unos milisegundos, que nadie nota al entrar; probar millones de candidatos tarda años. Agrega además una sal, un valor al azar distinto por contraseña que queda guardado adentro del mismo resultado, para que dos personas con la misma contraseña no queden con el mismo hash.

Implementación

// 1 · al crear el usuario: se guarda el resultado, nunca la contraseña
$hash = password_hash($clave, PASSWORD_DEFAULT);
// ese $hash va a la columna `clave`, que se define VARCHAR(255)

// 2 · al entrar: se compara sin leer nada
if (password_verify($clave_tecleada, $fila['clave'])) {
  $_SESSION['usuario'] = $fila['usuario'];
}

// 3 · lo que no se hace nunca
// $_SESSION['clave'] = $clave;   <- no se guarda
// echo $fila['clave'];           <- no se muestra
// error_log($clave);             <- no se registra
De dónde sale el VARCHAR(255)
Hoy PASSWORD_DEFAULT usa bcrypt, que produce 60 caracteres y empieza con $2y$. El manual de PHP avisa que ese algoritmo por omisión puede cambiar en versiones futuras, y otro algoritmo produce una salida más larga. Con 255 el sistema sigue funcionando el día que eso pase. Con 60 se rompe en silencio: MySQL guarda el hash cortado y el login deja de validar sin dar ningún error.

Cambios al publicar el sistema

Mientras el sistema corre en localhost, la contraseña vacía de MySQL y el error de PHP en pantalla no le hacen daño a nadie, porque nadie más llega a esa máquina. Publicado, cada una de esas cosas queda a la vista de cualquiera. El despliegue es lo que le da peso a todo lo anterior.

  • La credencial protege algo real. Ya no es root sin contraseña: el panel del hosting da un usuario y una clave que sí importan.
  • Los errores no se muestran. Cualquiera puede provocar uno y leer los nombres de las tablas.
  • Las direcciones se descubren. Un archivo que existe y no está enlazado igual se puede pedir: la página de prueba, el .sql, la que genera un hash.
  • El sitio queda a nombre del equipo. Lo que alguien cargue en un formulario aparece publicado con su dirección.

Los pasos concretos —cuenta, base en el servidor, exportar, importar, subir y el archivo de conexión del servidor— están en Publicar el sitio.
