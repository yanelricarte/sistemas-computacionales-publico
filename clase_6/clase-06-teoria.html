El sistema construido en las Clases 1 a 5

Un sistema informático recibe datos, los procesa y devuelve un resultado, trabajando sobre información que queda guardada. El sistema en el que venís trabajando funciona en la web: el usuario interactúa desde el navegador —el cliente— y un programa en PHP responde desde el servidor.

Ese sistema lo fuimos construyendo de manera progresiva, clase a clase: cada una sumó una capa sobre la anterior. En la Clase 2 apareció la puerta de entrada, el login, y con ella la sesión y la protección de las páginas internas, además de la cabecera y el pie que se reutilizan en todo el sitio. La Clase 3 agregó la navegación entre secciones y el control de versiones con Git, de modo que el proyecto quedara guardado y con historial. En la Clase 4 los datos ganaron un lugar propio: se mudaron a datos.php, y desde ahí la cartelera se arma sola al recorrerlos con foreach, mientras la ficha localiza un elemento buscándolo por su clave. La Clase 5, por último, llevó esa información a una base de datos real en MySQL, con su tabla, sus tipos de dato y sus consultas.

Lo que enhebra todo el recorrido es que cada paso reutiliza y ordena lo anterior: la protección se apoya en la sesión del login, la cartelera vive de los datos de datos.php, y la tabla de MySQL estructura la misma información que ya guardaba el array. Mirarlo así —como un solo sistema que fue creciendo— es justamente el trabajo de esta clase. El siguiente cuadro resume qué aportó cada una:

Conceptos clave

Tres ideas atraviesan todo el sistema. Vale detenerse en ellas.

Entidad, registro y campo

  • Entidad: la "cosa" del mundo real sobre la que guardás datos (una película, un paciente, un producto). Es el sustantivo principal del proyecto.
  • Registro (o fila): un caso concreto de esa entidad (la película Matrix).
  • Campo (o columna): cada dato de ese registro (título, año, género), y cada campo tiene un tipo (número, texto…).

La misma entidad, en dos representaciones

La entidad aparece de dos formas equivalentes, una por componente:

en datos.php (PHP)                        en MySQL (tabla)
-----------------------------             ------------------------------
'matrix' => [                             id | titulo | anio | genero
   'titulo' => 'Matrix',                  ---+--------+------+----------------
   'anio'   => 1999,          =====>       1 | Matrix | 1999 | Ciencia ficción
   'genero' => 'Ciencia ficción'
]
un array asociativo = una FILA (registro)
las claves          = las COLUMNAS (campos)

Un array asociativo es un registro; sus claves son los campos. Entender esto es ver que datos.php y la tabla hablan de lo mismo con distinta forma; es, además, la base sobre la que después los dos componentes se conectan.

Tipos de dato y clave primaria

  • Tipo de dato: cada campo guarda una clase de dato. INT para números (año, id); VARCHAR(n) para texto (título, género). Elegir el tipo es una decisión de diseño: un año guardado como texto no se ordena ni compara bien.
  • Clave primaria: una columna que identifica cada fila sin repetirse. Se usa un id autonumerado (AUTO_INCREMENT), no el título, porque el título puede repetirse o cambiar y el id no.

Lo que no puede fallar

Sobre esa base, hay un núcleo que tiene que funcionar sí o sí para dar el sistema por completo. Si algo de esto falla, se arregla antes que cualquier detalle:

  • Login y protección. Se entra con usuario y clave, y una página interna redirige al login si no hay sesión. Sin esto, cualquiera accede a todo: es la base de la seguridad del sistema.
  • Cartelera con foreach. La lista se arma sola recorriendo datos.php con foreach (mínimo 4 elementos): ese es el mecanismo que se pide.
  • Ficha con lookup. $arr[$id] ?? null muestra un elemento y avisa si no existe (no rompe con un id inválido).
  • Tabla con datos y una consulta. La tabla existe con clave primaria, tiene filas y corre un SELECT ... WHERE ....
  • Todo versionado. El avance está en el repositorio: si no está en GitHub, para el proyecto no existe.
Errores que suelen romper el núcleo
Olvidar session_start() (la protección no funciona) · foreach sobre la variable equivocada o falta de return en datos.php (cartelera vacía) · clave mal escrita en la ficha · comillas en valores numéricos en SQL.

La documentación del sistema

Documentar es dejar por escrito, en lenguaje claro, qué hace tu sistema, cómo está organizado y en qué estado está. Es una explicación del proyecto —aparte del código— pensada para que la lea una persona. Con un sistema documentado, alcanza con leer ese texto para entenderlo.

Propósito

La documentación cumple varias funciones a la vez. Permite que otra persona —el resto del grupo, la docente o quien retome el proyecto más adelante— comprenda el sistema con solo leerla. Funciona, además, como memoria del propio equipo: con el paso de las semanas, un texto claro conserva las decisiones que de otro modo se olvidan. A la hora de presentar el proyecto ordena lo que se muestra, porque deja a la vista qué se construyó y qué queda pendiente. Y mientras se escribe también ayuda a pensar el trabajo: al enunciar lo que falta, aparece con claridad el próximo paso.

La documentación en Markdown

La documentación se guarda en un archivo de texto con extensión .md, dentro del repositorio, para que viaje con el código y quede versionada. Ese archivo se escribe en Markdown: un formato que da estilo con símbolos sencillos y que GitHub muestra prolijo de forma automática. El repositorio del proyecto

El repositorio (el proyecto en GitHub, con Git) es donde vive todo: el código, el script .sql y la documentación. Versionar es guardar los avances como una historia de cambios (cada commit es una foto del proyecto en un momento). Dos ideas: si algo no está en el repositorio, para el proyecto no existe; y la documentación va junto al código, en el mismo repositorio.

El proyecto, por etapas

El sistema no termina en esta clase. La documentación deja anotado lo que sigue:

  1. Segunda entidad y relaciones: el proyecto tiene más de una entidad (película → director; turno → paciente). Se conectan con claves foráneas y se representan en un diagrama entidad-relación.
  2. Conexión PHP–MySQL: que la aplicación lea la tabla de la base. Ahí se unen los dos componentes.
  3. Login real y validaciones: usuarios guardados en la base y controles sobre los datos que se cargan.
  4. Pruebas y defensa: revisar que todo funcione y presentar el proyecto.

Síntesis

  • Lo construido en las Clases 1 a 5 es un solo sistema, hecho por capas, con dos componentes (aplicación PHP y base MySQL).
  • El sistema completo debe contener login, protección, includes, navegación, cartelera y ficha (PHP), y tabla con datos y consultas (MySQL).
  • El núcleo que no puede fallar: login+protección, cartelera con foreach, ficha con lookup, tabla con datos y una consulta, y todo versionado.
  • La misma entidad se representa como array (un registro) y como fila de la tabla; las claves son los campos/columnas.
  • Documentar es explicar el sistema por escrito, en Markdown, dentro del repositorio, en un documento vivo.
