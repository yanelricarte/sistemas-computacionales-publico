Segunda entidad y relaciones: claves foráneas y diagrama ER

En la Clase 5 hiciste una tabla. 0. De dónde venimos: una tabla sola

En la Clase 5 pasaste tus datos de datos.php a una tabla de MySQL. Aprendiste tres operaciones que siguen vigentes sin cambios:

  • CREATE TABLE — define la estructura: qué columnas hay y de qué tipo es cada una.
  • INSERT — carga filas.
  • SELECT / WHERE — consulta y filtra.

Y una columna especial: el id, la clave primaria, que identifica cada fila sin repetirse y la numera sola la base.

CREATE TABLE peliculas (
    id      INT AUTO_INCREMENT PRIMARY KEY,
    titulo  VARCHAR(100) NOT NULL,
    anio    INT,
    genero  VARCHAR(50)
);

Todo eso funciona. El problema aparece cuando querés guardar algo más que las películas.

De una tabla a un modelo
Hasta acá trabajaste con una tabla. A partir de esta clase vas a trabajar con un modelo: varias tablas que se conocen entre sí. El agregado de sintaxis es mínimo, dos líneas de SQL. La exigencia está en el diseño, porque tenés que decidir qué información corresponde a cada tabla.

1. El problema: el dato que se repite

Supongamos que ahora querés guardar también el director de cada película: su nombre y su nacionalidad. La solución más rápida consiste en agregar dos columnas a la tabla que ya tenés:

peliculas
titulo          │ anio │ genero    │ director     │ nacionalidad
────────────────┼──────┼───────────┼──────────────┼────────────────
Coco            │ 2017 │ Animación │ Lee Unkrich  │ Estados Unidos
Toy Story 3     │ 2010 │ Animación │ Lee Unkrich  │ Estados Unidos
Buscando a Nemo │ 2003 │ Animación │ Lee Unkrinch │ Estados Unidos
                                     ▲
                                     el mismo dato, escrito 3 veces
                                     (y la tercera, mal)

Esa tabla resuelve el pedido inicial y funciona mientras los datos sean pocos. A medida que el sistema crece, arrastra tres problemas que ya están presentes en esas tres filas:

1. Variantes del mismo dato escritas distinto

Lee Unkrich, Lee Unkrinch, lee unkrich. Para vos son la misma persona; para la base son tres directores distintos. Si buscás WHERE director = 'Lee Unkrich', la tercera película no aparece. Y no hay ningún error: la base guardó exactamente lo que le pediste.

2. Corrección de un dato repetido en muchas filas

Corregir un dato mal escrito obliga a recorrer cada una de las filas donde aparece. Con tres películas la tarea es tediosa; con trescientas, la probabilidad de omitir alguna es alta. Y una sola fila omitida deja a la base contradiciéndose a sí misma: el mismo director figura de dos maneras distintas según dónde se lo consulte.

3. Datos del director sin lugar propio

Con esta estructura, el director existe únicamente adentro de una película: para registrarlo tenés que cargar antes alguna película suya. Y si quisieras guardar su fecha de nacimiento, su biografía o su foto, esos datos quedarían repetidos en cada una de sus filas.

Cuándo un dato pide su propia tabla
Si un dato se repite fila tras fila y tiene datos propios, dejó de ser una columna: es una entidad y necesita su propia tabla.

El recurso para resolver los tres problemas ya lo conocés. En la Clase 5 aprendiste que cada fila lleva un id que la identifica de manera única, y esa es exactamente la pieza que falta acá: los directores pasan a su propia tabla, cada uno con su id, y en la tabla de películas queda únicamente ese número.

directores                              peliculas
id │ nombre       │ nacionalidad        titulo           │ director_id
───┼──────────────┼───────────────      ─────────────────┼─────────────
 2 │ Lee Unkrich  │ Estados Unidos      Coco             │      2
                                        Toy Story 3      │      2
   ▲                                    Buscando a Nemo  │      2
   escrito UNA sola vez                                        ▲
                                                    todas apuntan al mismo id

Ahora el nombre está escrito una vez. Si estaba mal, se corrige una vez y las tres películas quedan bien automáticamente, porque ninguna guarda el nombre: guardan el número.

Por qué el género se queda como columna

Antes de avanzar conviene atender una objeción razonable, porque la regla parece aplicarse de manera despareja: en la tabla de arriba, genero también se repite. "Animación" aparece en un montón de películas. ¿Por qué el director se va a otra tabla y el género no?

La respuesta está en que la regla tiene dos condiciones y ambas deben cumplirse. Del género guardás únicamente su nombre; del director guardás nacionalidad, año de nacimiento y, eventualmente, una foto y una biografía. Ese conjunto de atributos propios es lo que convierte al director en una entidad.

              ¿se repite?   ¿tiene datos propios?      ¿tabla aparte?
──────────────────────────────────────────────────────────────────────
director          sí        sí (nacionalidad, año…)         SÍ
genero            sí        no (solo el nombre)             no, por ahora
titulo            no        —                               no

Reparemos en ese "por ahora". Si más adelante tu proyecto necesitara guardar del género una descripción, un color o un ícono, el género pasaría a ser una entidad y tendría su propia tabla. La decisión se toma en función de lo que tu sistema necesite guardar sobre ese dato. Por eso hablamos de diseño: hay un criterio que aplicar, y la respuesta puede ser distinta en tu proyecto que en el de tu compañero.

Con el criterio resuelto y la segunda entidad identificada, queda por definir cómo se vinculan ambas tablas. De eso trata la sección siguiente.

2. La relación uno-a-muchos

Antes de escribir SQL hay que entender cómo se relacionan las dos entidades. Y eso se descubre diciéndolo en voz alta, en castellano, en los dos sentidos:

¿Cuántas películas puede tener un director?   →  MUCHAS
¿Cuántos directores puede tener una película?  →  UNA sola

Esa asimetría tiene nombre: es una relación uno-a-muchos, que se escribe 1:N. Y es la relación más común de todas: la vas a encontrar en casi cualquier proyecto.

Del lado del unoDel lado de los muchos
un directormuchas películas
un pacientemuchos turnos
una categoríamuchos productos
un libromuchos préstamos
un paísmuchas ciudades
La relación de tu proyecto
Armá la frase "cada ______ tiene un ______". Si te sale natural, ya tenés la relación. Después probá darla vuelta: "cada ______ tiene una sola ______". Si esa segunda frase te suena mal, es porque el lado de los muchos está al revés.

La ubicación del dato que conecta

Ahora la pregunta importante: la columna que conecta las dos tablas, ¿en cuál de las dos va?

Probemos al revés, para ver por qué no funciona. Si la conexión estuviera en directores, esa tabla necesitaría una columna por cada película:

directores  (así NO)
id │ nombre       │ pelicula_1 │ pelicula_2 │ pelicula_3 │ pelicula_4 │ ...
───┼──────────────┼────────────┼────────────┼────────────┼────────────┼────
 2 │ Lee Unkrich  │     7      │     12     │     15     │   (vacío)  │ ...
                       └──────────┴──────────┘
                       el id de cada una de sus películas

    ¿y si dirige 40 películas? ¿agregamos 40 columnas?

Imposible: no sabés de antemano cuántas van a ser. Un director puede tener una sola película o cuarenta, así que la tabla tendría que estar preparada para el peor caso, con casi todas las columnas vacías la mayor parte del tiempo.

Del otro lado, en cambio, el problema desaparece. Y vale la pena entender por qué, porque es lo que va a decidir todos los modelos que armes de acá en adelante: del lado de los muchos, la cantidad siempre es uno. Cada película tiene exactamente un director, y un dato del que sabés de antemano que va a ser uno solo se resuelve con una sola columna.

lado del UNO (directores)          lado de los MUCHOS (peliculas)
¿cuántas películas guarda?         ¿cuántos directores guarda?
   1, 5, 40… no se sabe    ✗          siempre 1               ✓
   → cantidad variable                → cantidad fija

Por eso la columna va donde la cantidad es fija.

El lado de la tabla donde va la clave foránea
La columna que conecta va siempre del lado de los muchos: director_id pertenece a peliculas. De acá en adelante vas a leer también otro par de nombres para las mismas dos tablas: la del lado del uno es la tabla apuntada (recibe la referencia) y la del lado de los muchos es la tabla que apunta (la contiene). Son dos maneras de nombrar lo mismo.

3. El diagrama entidad-relación

Todo lo anterior se dibuja. El diagrama entidad-relación (o diagrama ER) es el plano de tu base de datos: una caja por tabla, las columnas adentro, y una línea entre las cajas que muestra cómo se conectan.

    DIRECTORES                              PELICULAS
 ┌──────────────────┐                 ┌──────────────────────┐
 │ id  (PK)         │1              N │ id       (PK)        │
 │ nombre           ├─────────────────┤ titulo               │
 │ nacionalidad     │                 │ anio                 │
 │ anio_nac         │                 │ genero               │
 └──────────────────┘                 │ director_id  (FK) ───┼──► directores.id
                                      └──────────────────────┘

   el 1 y la N se leen así:
   "un director  ──1:N──►  muchas películas"
   "una película ────────►  un solo director"

La N representa "una cantidad cualquiera", y se usa justamente porque esa cantidad varía de una fila a otra. Poner un 1 de un lado y una N del otro es la forma abreviada de decir que a cada fila de la primera tabla le pueden corresponder muchas de la segunda, y que a cada una de esas le corresponde una sola de la primera. Se lee siempre en los dos sentidos, como cuando armaste la frase en castellano.

Todo diagrama ER, lo dibuje quien lo dibuje, tiene estas cinco piezas:

  1. Una caja por entidad. Arriba el nombre de la tabla, adentro las columnas.
  2. La clave primaria marcada en cada caja.
  3. Una línea que une las dos cajas.
  4. La cardinalidad en las puntas. El lado del uno (director) y el lado de los muchos (películas), cada uno con su marca.
  5. La clave foránea marcada, del lado de los muchos, indicando a qué apunta.
El diagrama va antes que el SQL
El diagrama se arma antes de escribir la primera línea de SQL. Corregirlo mientras es un diagrama lleva segundos; corregirlo cuando las tablas ya están creadas y cargadas implica rehacerlas. Ese es el orden de trabajo habitual en el desarrollo profesional, y por la misma razón.

La herramienta con la que vas a armarlo

Vas a usar databasediagram.com. Funciona directamente en el navegador, sin registrarte ni instalar nada: abrís la dirección y empezás a trabajar.

Se opera escribiendo: describís tus tablas en el panel de la izquierda y el diagrama se dibuja solo a la derecha. La sintaxis se parece bastante a la de un CREATE TABLE, así que vas a reconocerla — y eso juega a favor, porque lo que escribas acá es prácticamente el SQL que vas a escribir después. Para la cartelera queda así:

Table directores {
  id integer [pk]
  nombre varchar(100)
  nacionalidad varchar(50)
}

Table peliculas {
  id integer [pk]
  titulo varchar(100)
  anio integer
  genero varchar(50)
  director_id integer
}

ref: peliculas.director_id > directores.id

La última línea es la relación. El símbolo > significa muchos a uno y apunta desde el lado de los muchos hacia el lado del uno: muchas películas → un director. Si lo escribís al revés, el diagrama te va a salir invertido, y eso mismo te avisa que la FK está del lado equivocado.

La herramienta usa otra notación
El dibujo que obtengas va a diferir del de tu carpeta. La herramienta marca la cardinalidad con símbolos en las puntas de la línea: del lado de los muchos, una patita de tres trazos, llamada pata de gallo; del lado del uno, un trazo simple. Expresa exactamente lo mismo que tu 1───N. Son dos notaciones equivalentes para la misma idea, y vas a encontrar las dos en la bibliografía y en las herramientas profesionales.

4. Clave primaria y clave foránea

Llegado este punto conviene distinguir con precisión los dos tipos de clave que ya venís usando. La clave primaria y la clave foránea son ambas columnas de tipo INT y ambas guardan un número; la diferencia está en a quién identifican:

Clave primaria (PK)Clave foránea (FK)
Qué haceIdentifica la fila en su propia tablaApunta a una fila de otra tabla
Se repiteNunca: cada fila tiene la suyaSí: muchas películas pueden tener el mismo director
Quién la poneLa base, con AUTO_INCREMENTVos, al cargar la fila
Ejemplopeliculas.id, directores.idpeliculas.director_id

Una misma tabla puede tener las dos: peliculas tiene su id (PK, la identifica a ella) y además director_id (FK, apunta a otra tabla).

De dónde sale la palabra "foránea"
Foráneo significa de afuera, ajeno. Se llama así porque la clave que guarda esa columna no le pertenece: es la clave primaria de otra tabla, prestada. Por eso el 3 que ves en director_id cobra sentido únicamente al consultar la fila con id = 3 de directores: por sí mismo, dentro de peliculas, es apenas un número.

El nombre de la clave foránea

La columna se puede llamar como quieras, pero hay una convención que se usa en todos lados y te conviene respetar: el nombre de la tabla apuntada, en singular, más _id.

tabla apuntada          columna de la clave foránea
────────────────        ───────────────────────────
directores        →     director_id
pacientes         →     paciente_id
categorias        →     categoria_id
libros            →     libro_id

La convención tiene una finalidad práctica: permite interpretar de un vistazo un modelo escrito por otra persona. Si en una tabla ves una columna terminada en _id que no es la clave primaria, casi seguro es una clave foránea, y el propio nombre te está diciendo a qué tabla apunta. Es lo que vas a usar en la actividad de acá abajo.

Practicá: ¿PK, FK o columna común?

Arrastrá cada columna a su casillero. También podés tocar una tarjeta y después el casillero, o usar Enter con el teclado.

5. CREATE TABLE con FOREIGN KEY

Con el diagrama hecho, escribir el SQL es casi copiar. Pero hay una cosa nueva que importa mucho: el orden.

El orden de creación de las tablas
La tabla que recibe el apuntamiento (directores) tiene que existir antes que la que apunta (peliculas). Si lo hacés al revés, MySQL da error: no puede armar una referencia hacia una tabla que todavía no existe. 
-- 1) PRIMERO la tabla apuntada (el lado del "uno")
CREATE TABLE directores (
    id           INT AUTO_INCREMENT PRIMARY KEY,
    nombre       VARCHAR(100) NOT NULL,
    nacionalidad VARCHAR(50)
);

-- 2) DESPUÉS la que apunta (el lado de los "muchos")
CREATE TABLE peliculas (
    id          INT AUTO_INCREMENT PRIMARY KEY,
    titulo      VARCHAR(100) NOT NULL,
    anio        INT,
    director_id INT NOT NULL,                              -- la columna
    FOREIGN KEY (director_id) REFERENCES directores(id)    -- la regla
);

Comparalo con el CREATE TABLE de la Clase 5: es el mismo, más dos líneas.

  • director_id INT NOT NULL — la columna donde va a vivir el número.
  • FOREIGN KEY (director_id) REFERENCES directores(id) — la regla que la convierte en clave foránea.

Esa segunda línea es la que hace el trabajo de verdad. Leída en partes:

FOREIGN KEY ( director_id )  REFERENCES  directores ( id )
     │             │              │           │        └── a qué columna apunta
     │             │              │           └── a qué tabla apunta
     │             │              └── "apunta a"
     │             └── qué columna de ESTA tabla
     └── "esta columna es una clave foránea"

Para que MySQL acepte la regla, las dos columnas que se conectan tienen que ser del mismo tipo: si directores.id es INT, entonces peliculas.director_id también tiene que ser INT. Tiene sentido, porque una guarda una copia del valor de la otra: un texto no puede guardar un número. Si los tipos no coinciden, MySQL rechaza el CREATE TABLE entero.

La garantía que agrega esa línea

A partir de ahí, MySQL controla la relación por vos. Si alguien intenta guardar una película con un director_id que no existe, la base no lo deja. Eso se llama integridad referencial: la garantía de que ningún director_id apunta a una fila inexistente.

El riesgo de declarar la columna sin la regla
Podrías guardar el número en director_id sin declarar el FOREIGN KEY, y funcionaría. Pero nada impediría cargar un director_id = 99 con un director 99 que no existe, y esa película quedaría apuntando a la nada para siempre. La regla convierte ese error en un rechazo explícito de la base: en lugar de guardarse en silencio, la operación se detiene y MySQL avisa.

Para qué está ese NOT NULL

La cláusula anterior cubre un hueco; queda un segundo, de otra naturaleza. Corresponde hacer la precisión porque es la vía por la que se filtran datos incompletos. La clave foránea verifica los números que escribís; la obligación de escribir alguno depende del NOT NULL. Sin esa cláusula, la siguiente sentencia se ejecuta correctamente:

INSERT INTO peliculas (titulo, anio) VALUES ('Peli huérfana', 2024);
-- se guarda, con director_id en NULL: una película sin ningún director

Dicho de otro modo: la clave foránea garantiza que todo id escrito corresponde a una fila real, y el NOT NULL garantiza que ese id esté siempre presente. Las dos cláusulas combinadas expresan una única afirmación sobre tus datos: toda película tiene un director, y ese director existe.

Cuándo conviene dejarla sin NOT NULL
Se trata de una decisión de diseño que tomás según tu proyecto. Poné NOT NULL cuando la relación sea obligatoria (toda película tiene director; todo turno tiene paciente). Dejala sin NOT NULL cuando pueda faltar legítimamente — por ejemplo, si un producto puede estar todavía sin categoría asignada. En ese caso, NULL significa "acá falta el dato", que es distinto de un dato equivocado.
Cómo comprobar que la relación quedó declarada
Una vez ejecutados los dos CREATE TABLE, entrá a tu base en phpMyAdmin y abrí la pestaña Diseñador. Vas a ver tus dos tablas unidas por la línea de la relación. Lo valioso de esta vista es que la línea se dibuja únicamente cuando la clave foránea está declarada: si las tablas aparecen sueltas, la columna existe pero la regla falta.

El orden inverso para borrar las tablas

Si necesitás rehacer las tablas, el orden se invierte: primero se borra la que apunta.

DROP TABLE IF EXISTS peliculas;    -- primero la que apunta
DROP TABLE IF EXISTS directores;   -- después la apuntada

Con el orden al revés MySQL se niega, y tiene razón: quedarían películas apuntando a directores borrados.

6. INSERT: cargar respetando la relación

Mismo orden que al crear: primero las filas de la tabla apuntada. Una película no puede apuntar a un director que todavía no cargaste.

-- 1) PRIMERO los directores. No escribimos el id: lo pone la base.
INSERT INTO directores (nombre, nacionalidad) VALUES
    ('Lana Wachowski',  'Estados Unidos'),   -- va a quedar con id = 1
    ('Lee Unkrich',     'Estados Unidos'),   --                  id = 2
    ('Pete Docter',     'Estados Unidos');   --                  id = 3

-- 2) DESPUÉS las películas. En director_id va el ID, no el nombre.
INSERT INTO peliculas (titulo, anio, director_id) VALUES
    ('Matrix',       1999, 1),
    ('Coco',         2017, 2),
    ('Intensamente', 2015, 3);
El número que va en la clave foránea
En director_id se escribe el id del director. Poner ahí 'Lee Unkrich' es el error más frecuente de esta clase, y tiene una explicación razonable: el nombre es el dato que tenés presente mientras cargás. La columna, sin embargo, está declarada INT, y el vínculo con la otra tabla se establece a través del identificador.

¿Y cómo sabés qué id le tocó a cada director? Preguntándole a la base:

SELECT * FROM directores;

id │ nombre           │ nacionalidad
───┼──────────────────┼────────────────
 1 │ Lana Wachowski   │ Estados Unidos
 2 │ Lee Unkrich      │ Estados Unidos
 3 │ Pete Docter      │ Estados Unidos
Los ids no siempre arrancan en 1
Acá quedaron 1, 2 y 3 porque la tabla estaba recién creada y vacía. AUTO_INCREMENT lleva su propio contador y sigue avanzando: si ya tenías filas cargadas, si ejecutaste el INSERT dos veces o si borraste alguna fila, los números asignados van a ser otros. Consultá siempre el valor real con un SELECT antes de escribirlo en la clave foránea.

Probá que la regla existe

Conviene forzar el error una vez, de manera deliberada, para ver la regla en acción. Intentá cargar una película cuyo director_id no corresponda a ningún director cargado:

INSERT INTO peliculas (titulo, anio, director_id) VALUES ('Peli fantasma', 2024, 99);

MySQL responde algo así:

ERROR 1452: Cannot add or update a child row:
a foreign key constraint fails

Ese mensaje es la clave foránea funcionando: la base verificó si existía el director 99, comprobó que no, y rechazó la operación. Con el director guardado como texto suelto, tal como estaba en la Clase 5, esa misma fila se habría guardado sin observaciones y el error habría quedado latente en los datos.

7. SELECT: consultar por la clave foránea

Todo lo que sabés de la Clase 5 sigue funcionando igual. Lo nuevo es que ahora podés filtrar por la clave foránea, y eso responde una pregunta que antes no podías hacer: "¿qué películas dirigió esta persona?"

-- Cada tabla por separado
SELECT * FROM directores;
SELECT * FROM peliculas;      -- en director_id vas a ver el NÚMERO

-- Filtrar POR la clave foránea: las películas de un director
SELECT titulo, anio FROM peliculas WHERE director_id = 3;

Si no te acordás el id y sí el nombre, se hace en dos pasos:

-- Paso 1: conseguir el id
SELECT id FROM directores WHERE nombre = 'Pete Docter';
   -->  en esta base me devolvió 3 (en la tuya puede ser otro)

-- Paso 2: usar ESE número para filtrar
SELECT titulo, anio FROM peliculas WHERE director_id = 3;

El paso 1 es el que te da el número verdadero. Como vimos al cargar los datos, los ids dependen del historial de tu tabla, de modo que el 3 de este ejemplo probablemente corresponda a otro director en tu base.

El límite de consultar una tabla por vez

Cuando listás la cartelera, en la pantalla aparece esto:

titulo        │ anio │ director_id
──────────────┼──────┼─────────────
Intensamente  │ 2015 │      3          ← un número, no un nombre

Y lo que querrías ver es esto:

titulo        │ anio │ director
──────────────┼──────┼──────────────
Intensamente  │ 2015 │ Pete Docter

Traer las dos tablas combinadas en una sola consulta se resuelve con JOIN, que vamos a abordar cuando el proyecto lo requiera. Por ahora es suficiente con consultar cada tabla por separado. La prioridad de esta clase está en que el modelo quede bien construido, porque corregirlo más adelante resulta mucho más costoso.

Ampliación: las dos tablas en una sola consulta
Ejecutá esta sentencia y observá el resultado: 
SELECT peliculas.titulo, directores.nombre
FROM peliculas
JOIN directores ON peliculas.director_id = directores.id;
Esa sentencia combina las dos tablas. Leída en castellano: "traé el título de peliculas y el nombre de directores, uniendo aquellas filas donde el director_id coincide con el id".

y una regla, invisible en los datos pero activa todo el tiempo:
FOREIGN KEY (director_id) REFERENCES directores(id)

Tres cosas para chequear antes de dar la clase por cerrada:

  • El nombre de cada director está escrito una sola vez en toda la base. Ese era el problema con el que arrancamos.
  • Cada número de director_id existe en la otra tabla. De esa verificación se encarga la regla que declaraste.
  • El diagrama que armaste al principio y estas dos tablas describen la misma estructura. Ante cualquier diferencia entre ambos, conviene determinar cuál de los dos hay que corregir antes de seguir construyendo sobre el modelo.

8. Errores frecuentes

Mensaje / síntomaQué pasóCómo se arregla
Cannot add or update a child row: a foreign key constraint fails Estás cargando una fila con un id que no existe en la otra tabla. Correr SELECT * FROM la tabla apuntada y usar un id real. O cargar primero esa fila.
Cannot add foreign key constraint Creaste las tablas en el orden equivocado, o los tipos no coinciden. Crear primero la tabla apuntada. Y verificar que la PK y la FK sean del mismo tipo (las dos INT).
Cannot delete or update a parent row Querés borrar una tabla o una fila a la que otras están apuntando. Borrar primero la tabla (o las filas) que apuntan.
Field 'director_id' doesn't have a default value Hiciste un INSERT sin incluir la columna de la clave foránea, y la declaraste NOT NULL. Agregar director_id a la lista de columnas del INSERT, con un id que exista.
Guardaste el nombre en director_id La columna es INT: MySQL guarda un 0 o rechaza el dato. En la FK va el número. Buscar el id con un SELECT a la otra tabla.
La FK quedó en la tabla equivocada Pusiste pelicula_id en directores. Volver al diagrama: la FK va del lado de los muchos. Rehacer las tablas.
You have an error in your SQL syntax Falta la coma antes del FOREIGN KEY, o un paréntesis. El FOREIGN KEY va después de la última columna, separado por coma, adentro del paréntesis grande.

9. Glosario

TérminoQué significa
EntidadLa "cosa" del mundo real sobre la que guardás datos (película, director, paciente). Cada entidad es una tabla.
RelaciónEl vínculo entre dos entidades: "cada película tiene un director".
CardinalidadCuántos de un lado se corresponden con cuántos del otro. La que trabajamos acá es uno-a-muchos (1:N).
Clave primaria (PK)La columna que identifica cada fila en su propia tabla. Nunca se repite. Es el id.
Clave foránea (FK)Una columna que guarda el id de una fila de otra tabla. Sí se repite.
Integridad referencialLa garantía de que toda clave foránea apunta a una fila que existe de verdad. La hace cumplir MySQL.
RedundanciaEl mismo dato escrito muchas veces. Es lo que venimos a eliminar.
Diagrama EREl dibujo del modelo: una caja por tabla, líneas para las relaciones, PK y FK marcadas.
Modelo de datosEl conjunto de todas las tablas de tu sistema y cómo se relacionan entre sí.
