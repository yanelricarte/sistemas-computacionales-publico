0. Recuperación de la Clase 8: la web lee y agrega

Antes de sumar algo nuevo, repasemos lo que tu sistema ya hace. En la Clase 8 tu sitio dejó de leer un array escrito a mano y se conectó con la base: los datos pasaron a vivir en la base y la web empezó a pedirlos y a escribirlos por un canal llamado mysqli.

Las tres reglas que ya rigen tu proyecto

  1. La llave no se publica. conexion.php tiene el usuario y la contraseña de tu base: va en el .gitignore, y lo que se comparte es la plantilla documentada en el documentacion.md.
  2. El dato del usuario nunca va dentro de la consulta. Viaja aparte, en los ? de la sentencia preparada. Por el apóstrofo de Ocean's Eleven, que rompería la consulta, y por la inyección SQL, que es el caso grave.
  3. En la clave foránea va el id, no el nombre. El menú muestra el nombre y envía el número. Si ese número no existe en la otra tabla, la base rechaza la fila: es el error 1452.

1. Las cuatro operaciones: el CRUD

Casi todo lo que un sistema hace con sus datos entra en cuatro operaciones. Sus iniciales en inglés forman la sigla CRUD, y es vocabulario de oficio: se usa igual en cualquier lenguaje y con cualquier base de datos.

LetraOperaciónSQLEn tu proyecto
CCrear (create)INSERTEl formulario de alta — Clase 8
RLeer (read)SELECTEl listado del sitio — Clase 8
UActualizar (update)UPDATEEl formulario de edición — hoy
DBorrar (delete)DELETEEl botón de borrar — hoy
La idea de toda la clase
Las dos operaciones de hoy usan el mismo canal que ya tenés —mysqli, con tu conexion.php— y la misma familia de funciones. Lo que se suma es una cláusula que hasta ahora era opcional: WHERE, la que dice sobre cuál fila se trabaja.

En la Clase 6 usaste WHERE para filtrar un SELECT: leer solo las películas de un director. Hoy el mismo WHERE decide sobre qué filas se escribe: sin él, la operación se aplicaría a toda la tabla.

2. El id viaja por la URL: una fila sola

Si en el listado hay doce películas y querés corregir una, el programa tiene que saber cuál de las doce. El dato que sirve para señalarla es el id: es único en la tabla, ninguna otra fila tiene ese número. El título no sirve, porque dos películas pueden llamarse igual.

Ese número ya lo tenés a mano. El SELECT * del listado trae la columna id junto con las demás, así que dentro del while está disponible en $fila['id']. Con eso se arma un enlace por fila:

<?php
$resultado = mysqli_query($conexion, 'SELECT * FROM peliculas');
while ($fila = mysqli_fetch_assoc($resultado)) {
?>
  <article>
    <h2><?php echo $fila['titulo']; ?></h2>
    <p><?php echo $fila['anio']; ?></p>

    <a href="ficha.php?id=<?php echo $fila['id']; ?>">Ver</a>
    <a href="editar.php?id=<?php echo $fila['id']; ?>">Editar</a>
  </article>
<?php } ?>

El 3 de ficha.php?id=3 no lo escribís vos: lo pone PHP en cada vuelta del bucle, con el id de esa fila. Pasar un dato por la URL ya lo hiciste en las Clases 2 y 3 con info.php?seccion=…; lo único que cambia es qué dato viaja.

Traer una fila puntual

Del otro lado, la página lee el número con $_GET['id'] y pide a la base esa fila. Como el id es un dato que llega del navegador, entra a la consulta por sentencia preparada, igual que el título en el INSERT de la Clase 8:

<?php
// ficha.php
require 'conexion.php';

$id = $_GET['id'];

$stmt = mysqli_prepare($conexion, 'SELECT * FROM peliculas WHERE id = ?');
mysqli_stmt_bind_param($stmt, 'i', $id);
mysqli_stmt_execute($stmt);
$resultado = mysqli_stmt_get_result($stmt);
$pelicula  = mysqli_fetch_assoc($resultado);

if (!$pelicula) {
    die('No existe esa película.');
}
?>
<h1><?php echo $pelicula['titulo']; ?></h1>
<p>Año: <?php echo $pelicula['anio']; ?></p>
<p><a href="cartelera.php">← Volver al listado</a></p>

Lo nuevo del código es esto:

  • mysqli_stmt_get_result. Un INSERT no devuelve filas, así que en la Clase 8 alcanzaba con execute. Un SELECT sí devuelve filas: cuando la consulta va preparada, el resultado se pide con esta función y después se recorre como siempre.
  • Sin while. La consulta trae una sola fila, así que no hay nada que recorrer: se guarda en una variable. $pelicula es un array asociativo, el mismo de la Clase 4.
  • 'i' en bind_param. La letra declara el tipo del dato que se entrega: i para entero, s para texto.
El id puede venir mal
El id llega por la URL, y cualquiera puede escribir ficha.php?id=999 en la barra de direcciones. Cuando ese id no existe, mysqli_fetch_assoc devuelve null, y la página seguiría trabajando con una fila que no está: al llegar al echo, PHP avisa con Undefined array key "titulo". El if (!$pelicula) es lo que la detiene con un mensaje propio. Es la primera vez en el año que programás la respuesta a un dato inválido, y de acá en adelante es parte de escribir una página.

3. El formulario precargado

Para corregir un dato, el formulario tiene que abrir con la fila ya escrita en sus campos: nadie edita algo que aparece vacío. Eso es la ficha del punto anterior con un solo cambio: en vez de mostrar el dato en un <h1>, se muestra dentro del value de un <input>.

ficha.php                          editar.php

<h1><?php echo                     <input value="<?php echo
  $fila['titulo']; ?></h1>           $fila['titulo']; ?>">

mostrar la fila                     mostrar la fila DENTRO del campo

La consulta es idéntica. Lo que cambia es dónde va el echo:

<?php
// editar.php
require 'conexion.php';

$id = $_GET['id'];

$stmt = mysqli_prepare($conexion, 'SELECT * FROM peliculas WHERE id = ?');
mysqli_stmt_bind_param($stmt, 'i', $id);
mysqli_stmt_execute($stmt);
$pelicula = mysqli_fetch_assoc(mysqli_stmt_get_result($stmt));

if (!$pelicula) {
    die('No existe esa película.');
}
?>
<form method="POST" action="procesar_edicion.php">
  <input type="hidden" name="id" value="<?php echo $pelicula['id']; ?>">

  <label>Título:
    <input type="text" name="titulo"
           value="<?php echo htmlspecialchars($pelicula['titulo']); ?>" required>
  </label>

  <label>Año:
    <input type="number" name="anio" value="<?php echo $pelicula['anio']; ?>">
  </label>

  <button>Guardar cambios</button>
</form>

El campo oculto: cuál fila se está editando

El formulario de alta de la Clase 8 y este se parecen mucho, y hacen cosas distintas: uno crea una fila nueva, el otro modifica una que ya existe. Por eso el de edición necesita un dato más — cuál fila —, y ese dato es el id.

Viaja en un <input type="hidden">: no se dibuja en la pantalla, y el navegador lo envía junto con el resto del formulario. Es el puente entre el ?id=3 que llegó por GET y el POST que va al procesador. Sin ese campo, el UPDATE no sabe a cuál fila modificar.

Oculto para el usuario, visible para el navegador
"Oculto" quiere decir que no se muestra, no que sea intocable: quien sabe usar las herramientas del navegador puede cambiar ese número y mandar el formulario con otro id. Hoy alcanza para que el sistema funcione; cuando el sistema tenga usuarios, además de recibir el id va a tener que comprobar quién lo manda. Ese es el tema de la próxima clase.
htmlspecialchars, otra vez y con motivo
Un título con comilla doble —El "Zorro"— cierra el value=" antes de tiempo y el campo aparece cortado. htmlspecialchars convierte esa comilla en algo que el navegador muestra sin interpretarlo. Es el mismo cuidado de la Clase 1 (la salida del usuario se escapa), aplicado a un atributo HTML: el hermano del apóstrofo que rompía el INSERT en la Clase 8.

El desplegable de la clave foránea

El menú de la FK ya lo escribiste en la Clase 8: consulta la otra tabla y arma las <option> con value = id y texto = nombre. Falta una sola cosa: marcar cuál de todas es la de esta fila. Eso lo hace el atributo selected, en una sola opción — la que coincide.

<label>Director:
  <select name="director_id">
    <?php
    $directores = mysqli_query($conexion, 'SELECT id, nombre FROM directores ORDER BY nombre');
    while ($d = mysqli_fetch_assoc($directores)) {
    ?>
      <option value="<?php echo $d['id']; ?>"
        <?php if ($d['id'] == $pelicula['director_id']) { echo 'selected'; } ?>>
        <?php echo $d['nombre']; ?>
      </option>
    <?php } ?>
  </select>
</label>
== compara, = asigna
La condición usa ==, la comparación de la Clase 4. Con un solo = el programa asigna en lugar de comparar: la condición se queda con el valor asignado, se cumple, y todas las opciones salen marcadas. Y si te olvidás la comparación entera, el menú abre en el primer director de la lista: quien guarde sin tocar el menú le cambia el director a la película sin que nada avise. Es un error que no da mensaje — se ve en pantalla, abriendo dos filas con distinto director.

4. Guardar los cambios: UPDATE

El formulario manda sus datos por POST al procesador, que hace el UPDATE y devuelve al listado. Es el mismo recorrido del alta de la Clase 8, con otra instrucción SQL:

<?php
// procesar_edicion.php
require 'conexion.php';

$id          = $_POST['id'];
$titulo      = $_POST['titulo'];
$anio        = $_POST['anio'];
$director_id = $_POST['director_id'];

$stmt = mysqli_prepare($conexion,
    'UPDATE peliculas SET titulo = ?, anio = ?, director_id = ? WHERE id = ?');
mysqli_stmt_bind_param($stmt, 'siii', $titulo, $anio, $director_id, $id);
mysqli_stmt_execute($stmt);

header('Location: cartelera.php?ok=guardado');
?>

La instrucción tiene tres partes y se lee en ese orden. Para escribirla conviene empezar por el WHERE: el recuadro de abajo explica por qué.

UPDATE peliculas                                   ¿qué tabla?
   SET titulo = ?, anio = ?, director_id = ?       ¿qué columnas cambian?
 WHERE id = ?                                      ¿sobre cuál fila?

Las columnas que no aparecen en el SET quedan como estaban. El WHERE es el que limita la operación a una fila.

El id va último en bind_param
El orden de los valores sigue el orden de los ? en la consulta. El ? del WHERE está escrito al final, así que el $id es el último de la lista, y 'siii' lleva una letra por cada uno: texto para el título, entero para el año, para la clave foránea y para el id. Si cambiás el orden, PHP no da error de sintaxis: guarda el dato en la columna equivocada, o modifica otra fila.
La línea que no se olvida: sin WHERE se afecta toda la tabla

Estas dos consultas no fallan. Hacen exactamente lo que se les pidió:

UPDATE peliculas SET anio = 1900;    →  12 filas afectadas
DELETE FROM peliculas;              →  la tabla queda vacía

No hay botón de deshacer. Lo que te protege es el hábito de escribir el WHERE antes que el SET, el número de filas afectadas que informa phpMyAdmin —que avisa cuando esperabas una fila y toca doce— y la copia: el .sql que exportaste al repositorio en las Clases 5 y 7. El código está en Git; los datos, solo en ese archivo.

Si querés verlo sin riesgo, hacelo sobre una copia: en phpMyAdmin, Operaciones → Copiar tabla a… (con estructura y datos) a peliculas_prueba, corré el UPDATE sin WHERE ahí, mirá el resultado y después DROP TABLE peliculas_prueba;.

5. Avisarle al usuario

Guardás un cambio, volvés al listado y la página no dice nada. El dato cambió, pero el sistema no lo comunica: el usuario tiene que ir a buscar la fila para comprobar si su clic sirvió. Confirmar lo que se hizo es parte del trabajo del sistema.

Hay un detalle técnico que explica por qué el aviso no se escribe en el procesador: el header('Location: …') le dice al navegador que pida otra página, y esa página nueva no sabe nada de lo que pasó en la anterior. Así que el aviso viaja donde puede viajar: en la URL.

<?php
// procesar_edicion.php  (al final)
header('Location: cartelera.php?ok=guardado');
?>
<?php
// cartelera.php  (arriba del listado)
$aviso = $_GET['ok'] ?? '';

if ($aviso === 'guardado') { echo '<p class="aviso">Los cambios se guardaron.</p>'; }
if ($aviso === 'borrado')  { echo '<p class="aviso">La fila se borró.</p>'; }
?>

El ?? es el de la Clase 4: si en la URL no viene ok, $aviso queda vacío y no se muestra nada. Sin él, entrar al listado directo daría Undefined array key "ok". En el estilos.css, una regla mínima para .aviso (un fondo suave y un borde) alcanza: el aviso tiene que verse distinto del contenido.

Un límite conocido
El aviso queda en la URL, así que recargar la página lo repite. La forma seria de resolverlo son las sesiones —las que ya usás para el login desde la Clase 2—: guardar el mensaje una vez, mostrarlo y borrarlo. Se retoma en la próxima clase.

6. Borrar: DELETE con confirmación

La solución rápida sería un enlace por fila: borrar.php?id=3. El problema está en lo que un enlace permite: se sigue sin querer —un clic de más, el botón atrás del navegador—, se comparte, se guarda en favoritos, y hay navegadores que lo abren por adelantado para tenerlo listo. Un borrado no puede depender de eso.

La regla: GET muestra, POST modifica
Una página que muestra algo se pide por GET (así viaja el ?id=3 de la ficha). Una acción que modifica datos se manda por POST, desde un formulario con su botón. Los dos los venís usando desde la Clase 1; lo que se agrega hoy es el criterio para elegir.

Con esa regla, el borrado queda en dos pasos. El primero es la ficha del punto 2 con otra pregunta:

<?php
// borrar.php  — llega por GET, con ?id=3
require 'conexion.php';

$id = $_GET['id'];

$stmt = mysqli_prepare($conexion, 'SELECT * FROM peliculas WHERE id = ?');
mysqli_stmt_bind_param($stmt, 'i', $id);
mysqli_stmt_execute($stmt);
$pelicula = mysqli_fetch_assoc(mysqli_stmt_get_result($stmt));

if (!$pelicula) {
    die('No existe esa película.');
}
?>
<p>¿Borrar <strong><?php echo htmlspecialchars($pelicula['titulo']); ?></strong>?
   Esta acción no se puede deshacer.</p>

<form method="POST" action="procesar_borrado.php">
  <input type="hidden" name="id" value="<?php echo $pelicula['id']; ?>">
  <button>Sí, borrar</button>
</form>
<p><a href="cartelera.php">Cancelar</a></p>

Y el segundo paso, que es el que toca la base:

<?php
// procesar_borrado.php  — llega por POST
require 'conexion.php';

$id = $_POST['id'];

$stmt = mysqli_prepare($conexion, 'DELETE FROM peliculas WHERE id = ?');
mysqli_stmt_bind_param($stmt, 'i', $id);
mysqli_stmt_execute($stmt);

header('Location: cartelera.php?ok=borrado');
?>

Nombrar la fila es parte de la confirmación. Un cartel que dice "¿Seguro?" sin decir qué se va a borrar no informa nada. En el listado, el botón de borrar de cada fila sí puede ser un enlace a borrar.php?id=…: esa página pregunta, no modifica.

La ventanita del navegador
En muchos sistemas la confirmación es un cartel de JavaScript (confirm()). La vas a ver en todas partes y está bien conocerla, pero no reemplaza a esta página: si el navegador tiene el JavaScript desactivado, la ventanita no aparece y el borrado sigue igual. La confirmación que vale es la que decide el servidor.

Borrar una fila que está apuntada

Probá borrar un director que tenga películas cargadas. La base se niega:

ERROR 1451: Cannot delete or update a parent row:
            a foreign key constraint fails

Es el hermano del 1452 de la Clase 7. Entonces la base impidió cargar una película que apuntaba a un director inexistente; ahora impide borrar un director que dejaría películas apuntando al vacío. Las dos son la misma garantía —integridad referencial— mirada de cada lado.

Que la base frene el borrado es lo correcto. Lo que falta es que el sistema lo explique, en lugar de mostrar un error de PHP:

<?php
// procesar_borrado_director.php
if (mysqli_stmt_execute($stmt)) {
    header('Location: directores.php?ok=borrado');
} else {
    header('Location: directores.php?error=tiene_peliculas');
}
?>

Del otro lado, el mismo mecanismo del punto 5 con otro texto: "No se puede borrar: tiene películas cargadas." El aviso de error usa el mismo mecanismo que el de éxito.

Tres salidas cuando una fila está apuntada
Cuando una fila tiene otras que la apuntan, un sistema puede negarse a borrarla (lo que hace la base por defecto), borrar también las hijas (ON DELETE CASCADE) o dejarlas sin referencia. Cuál corresponde depende del proyecto: borrar un director no debería borrar sus películas, pero borrar un pedido probablemente sí deba borrar sus renglones. Es una decisión que cada grupo va a tomar sobre su propio modelo.

El UPDATE guarda el dato en la columna equivocada El orden de los valores de bind_param no coincide con el orden de los ?. Leer la consulta de izquierda a derecha y poner los valores en ese orden. El id del WHERE, último.
Se modificaron todas las filas de la tabla Al UPDATE le faltó el WHERE. Reimportar el .sql del repositorio. Después, escribir siempre el WHERE antes que el SET.
Cannot delete or update a parent row (1451) La fila que se quiere borrar está apuntada por una clave foránea. Es correcto que la base lo impida: mostrar un aviso al usuario en vez del error.
El aviso ?ok=guardado no aparece El listado no lee $_GET['ok'], o el header redirige sin el parámetro. Mirar la barra de direcciones: si el parámetro está, el problema está en el if.
Warning: Cannot modify header information Se imprimió algo (un espacio, un echo, HTML) antes del header('Location: …'). El procesador no muestra nada: la redirección va antes de cualquier salida.

Glosario

TérminoQué significa
CRUDLas cuatro operaciones básicas sobre datos: crear, leer, actualizar y borrar (INSERT, SELECT, UPDATE, DELETE).
WHERELa cláusula que dice sobre cuáles filas trabaja una consulta. En UPDATE y DELETE es lo que evita afectar la tabla entera.
UPDATEInstrucción SQL que modifica columnas de las filas que cumplen el WHERE.
SETLa parte del UPDATE que enumera qué columnas cambian y con qué valor.
DELETEInstrucción SQL que elimina las filas que cumplen el WHERE.
Filas afectadasLa cantidad de filas que una operación modificó o borró. Es la señal para darse cuenta de que un WHERE falta o está mal.
mysqli_stmt_get_resultPide el resultado de una consulta preparada que devuelve filas (un SELECT), para después recorrerlo con fetch_assoc.
Campo oculto<input type="hidden">: no se dibuja en la pantalla, y el navegador lo envía con el formulario. Es como viaja el id.
Formulario precargadoUn formulario que abre con los datos de una fila escritos en sus campos, listos para corregir.
valueEl atributo que define lo que un campo muestra al abrirse.
selectedEl atributo que marca cuál <option> aparece elegida al abrir un <select>.
htmlspecialcharsConvierte los símbolos con significado en HTML (<, >, ", &) para que se muestren en vez de interpretarse.
GET / POSTLas dos formas de pedir una página. GET para mostrar (los datos van en la URL), POST para modificar (van en el cuerpo del pedido).
Error 1451El rechazo de MySQL a borrar una fila apuntada por una clave foránea. El 1452 es el rechazo a cargar una FK que no existe.
Borrado lógicoMarcar una fila como inactiva en vez de eliminarla, para poder recuperarla. Se usa en la mayoría de los sistemas reales.

1. Para modificar una fila, ¿con qué dato conviene señalarla?

2. En el listado, ¿de dónde sale el 3 de editar.php?id=3?

3. ¿Por qué el SELECT preparado necesita mysqli_stmt_get_result y el INSERT de la Clase 8 no lo necesitaba?

4. ¿Qué previene el if (!$pelicula) { die(…); } después de traer la fila?

5. ¿Para qué está el <input type="hidden" name="id"> en el formulario de edición?

6. Una película se llama El "Zorro" y en el formulario el campo aparece cortado. ¿Qué pasó?

7. El formulario de edición abre siempre con el primer director del menú. Se corrige solo el año y se guarda. ¿Qué pasa?

8. En 'UPDATE peliculas SET titulo = ?, anio = ? WHERE id = ?', ¿en qué orden van los valores en bind_param?

9. ¿Qué hace UPDATE peliculas SET anio = 1900; tal como está escrito?

10. ¿Por qué el borrado se manda por POST y no con un enlace borrar.php?id=3 que borre directo?

11. Al borrar un director con películas cargadas aparece el error 1451. ¿Qué significa?

12. ¿Por qué el mensaje "Los cambios se guardaron" viaja en la URL (?ok=guardado)?

¿Ya terminaste? Pasá al TP de Clase 9 — ahí tu web pasa a modificar y borrar filas de tus dos tablas.

7. Próximos pasos

Con esta clase el CRUD queda completo: tu sistema crea, lee, modifica y borra los datos de sus dos entidades. Con eso aparece un problema nuevo, que es la señal de que el sistema ya hace algo importante:

Cualquiera que escriba en la barra de direcciones

    borrar.php?id=3

llega a la confirmación y puede borrar una fila.

Las páginas que modifican datos no saben quién está del otro lado. En el sistema hay un login desde la Clase 2, pero con el usuario y la contraseña escritos en el código, y no protege a estas páginas nuevas. La próxima clase lo lleva a la base: una tabla de usuarios, las contraseñas guardadas como corresponde (password_hash, nunca en texto plano), las páginas de edición y borrado protegidas, y la comprobación de los datos hecha en el servidor.
